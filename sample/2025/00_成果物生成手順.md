# 2025年テストベース基準 成果物生成手順

本書は `sample/2025/` 配下の成果物を **誰でも同じ入力から同じ出力に再生成できる** ようにするための手順書である。
対象は ASTER テスト設計コンテスト 2025年版テストベース（`sample/2025/2025_tdc_open_testbase/` の PDF 9文書）。

追跡: GitHub Issue #73（親 #69） / Jira HSKZ-117。

---

## 1. 工程の全体像

| 工程 | 内容 | 使用ツール | 状態 | 成果物 |
| --- | --- | --- | --- | --- |
| **A** | ID母集団監査（実在ID母集団と対象／除外の理由付き宣言の確定） | `audit_id_population` | **実施済み** | `sample/2025/01_ID母集団監査_2025テストベース.md` |
| **B** | テスト計画書の生成・レビュー・修正・改訂・再検証 | `create_test_plan` / `review_test_plan` / `revise_test_plan` | **実施済み** | `sample/2025/02_テスト計画書_初版.md`〜`sample/2025/06_テスト計画書レビュー結果_改訂版.md` |
| **C-1** | テスト分析（要件分析・テストベースレビュー・仕様齟齬指摘） | `analyze_requirements` / `review_test_basis` | **実施済み（本コミット）** | `sample/2025/07_要件分析結果_2025テストベース.md`〜`sample/2025/09_テストベース仕様齟齬指摘_2025テストベース.md` |
| **C-2** | テスト分析（利用状況モデリング・テスト条件抽出） | `generate_user_story_map` / `extract_test_conditions` | **実施済み** | `sample/2025/10_利用状況モデリング結果.md` / `sample/2025/11_テスト条件抽出結果.md` |
| **D-1** | テスト設計（境界値分析・同値分割） | `design_boundary_values` / `design_equivalence_partitioning` | **実施済み（本コミット）** | `sample/2025/12_境界値分析結果.md` / `sample/2025/13_同値分割結果.md` |
| D-2 | テスト設計（テストケース生成） | `generate_test_cases` | 未実施 | - |
| D-3 | テスト設計（探索的チャーター・テスト仕様レビュー） | `generate_exploratory_charters` / `review_test_specification` | 未実施 | - |
| E | 2026年版との差分再展開 | `reexpand_threshold_changes` | 未実施 | - |

**工程B〜Eはすべて工程Aで確定した母集団を分母として使う。** 工程Aの宣言（`sample/2025/payloads/audit-id-population.json`）と
実際に工程B〜Dへ投入した母集団が食い違った場合は、payload を直して工程Aを再実行し、差分を成果物に反映する。

## 2. 前提の導入

### 2.1 poppler-utils（`pdftotext`）

テストベースは PDF でのみ提供される。全文テキスト化に `pdftotext` を使う。

```
# Debian / Ubuntu
apt-get update && apt-get install -y poppler-utils
# macOS
brew install poppler
# Windows
winget install --id oschwartz10612.Poppler
```

未導入のまま `scripts/extract-testbase-text.sh` を実行すると、導入コマンドを表示して非0終了する。

**本調査で使用した `pdftotext` は poppler 24.02.0 である。**
`sample/2025/09_テストベース仕様齟齬指摘_2025テストベース.md` および本書 第7章・第8章に記載した行番号は、
すべて `.work/testbase/2025/*.txt`（この版で抽出したテキスト）の行番号である。poppler のバージョンが変わると
改行位置が変化し**行番号がずれる可能性がある**（本調査では同一バージョンでの再抽出が完全一致することを確認済み）。
行番号が合わない場合は、まず `pdftotext -v` で版を確認すること。

## 3. 実行コマンド

### 3.1 工程A: ID母集団監査

```
# 1. テストベースPDFを全文テキスト化（-> .work/testbase/2025/*.txt が9件）
bash scripts/extract-testbase-text.sh 2025

# 2. audit_id_population を実行して監査結果を生成
node scripts/call-mcp-tool.mjs \
  --tool audit_id_population \
  --payload sample/2025/payloads/audit-id-population.json \
  --documents-dir .work/testbase/2025 \
  --documents-key documents \
  --out "sample/2025/01_ID母集団監査_2025テストベース.md"
```

`scripts/call-mcp-tool.mjs` は `--documents-dir` のディレクトリ内の `*.txt` をファイル名昇順で読み、
`{name, content}` 配列として payload の `--documents-key` へ注入する。`name` は拡張子を除いたファイル名になる。

`--text-file` は指定ファイルをUTF-8で読み、文字列として payload の `--text-key`（既定 `planMarkdown`）へ注入する。
`review_test_plan` / `revise_test_plan` のように生成済み markdown を丸ごと入力に取るツールで、payload JSON に本文を
埋め込まずに投入するために使う。`--documents-dir` と同じく、payload に当該キーが既にある場合と、
指定ファイルが空の場合はエラーで停止する。

### 3.2 工程Aの再現性確認

```
bash scripts/extract-testbase-text.sh 2025 \
  && ls .work/testbase/2025/*.txt | wc -l \
  && node scripts/call-mcp-tool.mjs --tool audit_id_population \
       --payload sample/2025/payloads/audit-id-population.json \
       --documents-dir .work/testbase/2025 --documents-key documents \
       --out .work/audit-rerun.md \
  && diff .work/audit-rerun.md "sample/2025/01_ID母集団監査_2025テストベース.md" \
  && grep -n "未宣言: 0 " "sample/2025/01_ID母集団監査_2025テストベース.md" \
  && grep -n "未投入文書数: 0" "sample/2025/01_ID母集団監査_2025テストベース.md"
```

`.txt` が9件、`diff` が無出力になれば、コミット済みの監査結果は payload から完全に再生成できている。

### 3.3 工程B: テスト計画書の生成・レビュー・修正・改訂・再検証

工程Bの3ツールは**テストベース文書を入力に取らない**（`create_test_plan` の入力は `generateTestPlanInputShape` の
フィールドのみ、`review_test_plan` は `planMarkdown` のみ、`revise_test_plan` は `planMarkdown` と `instructions` のみ）。
したがって `--documents-dir` は使わず、テストベースの記述内容は payload の各フィールドへ人手で書き起こす。
記述の裏付けは実装者が担保する（3ツールの決定的検査はテンプレート41章の欠落・`_未記入（必須）_` の残存・
曖昧語レキシコン27語の出現の3種のみで、**テストベースとの照合は行わない**）。

```
# B-1 初版ドラフトの生成
node scripts/call-mcp-tool.mjs --tool create_test_plan \
  --payload sample/2025/payloads/test-plan-draft.json \
  --out "sample/2025/02_テスト計画書_初版.md"

# B-2 初版のレビュー（必須未記入9件が検出される）
node scripts/call-mcp-tool.mjs --tool review_test_plan \
  --payload sample/2025/payloads/review-test-plan.json \
  --text-file "sample/2025/02_テスト計画書_初版.md" --text-key planMarkdown \
  --out "sample/2025/03_テスト計画書レビュー結果_初版.md"

# B-3 レビュー指摘を修正指示に変換（機械的修正の適用結果を含む）
node scripts/call-mcp-tool.mjs --tool revise_test_plan \
  --payload sample/2025/payloads/revise-test-plan-draft.json \
  --text-file "sample/2025/02_テスト計画書_初版.md" --text-key planMarkdown \
  --out "sample/2025/04_テスト計画書修正指示_初版.md"

# B-4 改訂版の生成（工程C・Dが参照する確定版テスト計画書）
node scripts/call-mcp-tool.mjs --tool create_test_plan \
  --payload sample/2025/payloads/test-plan-revised.json \
  --out "sample/2025/05_テスト計画書_改訂版.md"

# B-5 改訂版の再検証
node scripts/call-mcp-tool.mjs --tool review_test_plan \
  --payload sample/2025/payloads/review-test-plan.json \
  --text-file "sample/2025/05_テスト計画書_改訂版.md" --text-key planMarkdown \
  --out "sample/2025/06_テスト計画書レビュー結果_改訂版.md"
```

`sample/2025/payloads/review-test-plan.json` は `{}` であり、初版レビュー（B-2）と改訂版レビュー（B-5）の双方で
再利用する。`planMarkdown` は `--text-file` から注入されるため、payload に本文を持たせない。

### 3.6 工程C-1: 要件分析とテストベースレビュー

工程C-1の2ツールは**テストベース9文書の全文を入力に取る**（工程Aと同じ投入方法）。

```
npm run build
bash scripts/extract-testbase-text.sh 2025

# C-1-1 要件分析（要件ID体系・数量表現の矛盾・境界値候補・用語の表記ゆれ・根拠位置）
node scripts/call-mcp-tool.mjs --tool analyze_requirements \
  --payload sample/2025/payloads/analyze-requirements.json \
  --documents-dir .work/testbase/2025 --documents-key documents \
  --out "sample/2025/07_要件分析結果_2025テストベース.md"

# C-1-2 テストベースレビュー（ID重複・未解決参照・プレフィックス逸脱・曖昧語・数量表現）
node scripts/call-mcp-tool.mjs --tool review_test_basis \
  --payload sample/2025/payloads/review-test-basis.json \
  --documents-dir .work/testbase/2025 --documents-key documents \
  --out "sample/2025/08_テストベースレビュー結果_2025テストベース.md"
```

`sample/2025/payloads/review-test-basis.json` は `{}` である。`reviewTestBasisInputShape` は
`documents` / `idPatterns` / `additionalAmbiguousTerms` の3キーだけで、`documents` は `--documents-dir` から注入される。

**2ツールのどちらにも `idPatterns` と `additionalAmbiguousTerms` を渡さない。** 渡すと抽出ID数・重複ID数・
曖昧語出現数がすべて変わり、工程A（`01_ID母集団監査_2025テストベース.md`）の母集団件数と直接比較できなくなる。
`analyze_requirements` の `qualityCharacteristicIds` も指定しない（8特性すべてをマッピング指示として出す）。

`09_テストベース仕様齟齬指摘_2025テストベース.md` は**ツール出力ではなく手書き**である。`review_test_basis` の入力は
`documents` のみで、生成済み markdown を入力に取る口を持たないため、「自分の成果物に対して `review_test_basis` を
実行する」ことは仕様上できない。`08_` の2章 意味的レビュー用チェックリスト（TB-01〜TB-13）を人手で適用した結果を
`09_` として成果物化している。したがって `09_` は次節の再現性 `diff` の**対象外**である。

読み取りの注意点:

- **`07_` 2.6 の根拠位置は439行だが、ユニークな定義IDは162件である。** 同じIDが機能一覧と詳細記述の両方に現れるため、
  出現箇所数（439）とID件数（162）が一致しない。162 は `01_ID母集団監査_2025テストベース.md` 2.8 の「定義ID総数: 162」と一致する。
  同じ理由で `07_` 2.1 および `08_` 1.2 の「定義数」は**出現箇所数であってID件数ではない**。
- **`07_` 2.2 の「秒」行に `30` と `60` の両方が現れる**（Issue #73 項目3が求めた `30秒` / `60秒`）。実測の行は
  `| 秒 | 25 | 1, 2, 5, 10, 30, 59, 60 | 以内 | 11号, 12号, 13号, 71号, 72号 | 要確認 |`
  （出現文書欄は実際には略号ではなくファイル名がそのまま入る）。内訳は 30秒＝11号:1240（残数表示インジケータ2の30秒周期）・
  11号:1656（時間枠別残数情報を30秒おきに受信）、60秒＝72号:249（「入場管理」→「クラウド２」のタイミング）、
  59秒＝71号:142（29分59秒99999…）。同じ矛盾候補が `07_` 3章 F-154 にも高重大度で現れる。
- **`08_` 1.3 の重複ID 144件は144件の仕様欠陥ではない。** 1文書内の重複113件・文書間の重複31件で、大半は機能一覧と
  詳細記述の再掲・画面仕様書での再定義である。別機能への重複採番は `EH-100` / `EH-210` / `EH-900` の3IDのみ
  （`09_` の SF-01〜SF-03）。`08_` 1.4 の `S-003-0` は 11号:476 行末で折り返された `S-003-02` であり、
  PDF→テキスト変換に起因する**偽陽性**である（`09_` の SF-11）。**決定的検査の件数をそのまま仕様欠陥の件数として扱わない。**
- **`07_` の4章（品質特性マッピング表）・5章（ステークホルダー別影響）・3章末尾の追記指示は、呼び出し側LLMへの指示と
  空表であり、ツール出力には内容が埋まらない。** これらに対応する意味的成果は `09_` に置いている。
- **抜粋検出の `[medium]` 4件（01号・02号・12号・72号の「検出IDが0件」）は9文書全文を投入しても残る。**
  工程A（`01_ID母集団監査_2025テストベース.md` 第6章）と同じ結果であり、文書の性格による正常な結果である。
  0件にするために抜粋を投入したり `idPatterns` を調整したりしてはならない（`09_` の SF-12）。

### 3.9 工程C-2a: 利用状況モデリング（ドメイン分析・ペルソナ4象限・ユーザーストーリーマップ・テスト要求）

`generate_user_story_map` は**テストベース文書を入力に取らない**。入力は payload だけであり、`--documents-dir` は使わない。

```
npm run build
node scripts/call-mcp-tool.mjs --tool generate_user_story_map \
  --payload sample/2025/payloads/generate-user-story-map.json \
  --out "sample/2025/10_利用状況モデリング結果.md"
```

payload に**テストベース本文を埋め込まない**方針は工程A・工程C-1と同じである（第4章）。payload に持たせるのは
ドメイン分析の把握した事実・ペルソナの4象限・5階層のマップ・テスト要求であり、各記述の末尾に根拠位置を
`文書名:行番号` 形式（`09_` 0.1 と同じ表記、poppler 24.02.0 での抽出行）で添えている。逐語の引用はせず、ID・機能名・
画面名・章節見出しと短い語句にとどめている。

`idPrefixes` は渡さない。既定の `ACT-` / `TSK-` / `US-` / `TR-` を使い、IDはいずれもゼロ埋め2桁で

## 4. テストベース全文テキストをコミットしない方針

`scripts/extract-testbase-text.sh` の出力先は `.work/testbase/<year>/` で、`.gitignore` により Git 管理外にしている。

理由:

- 抽出テキストは ASTER 提供資料（テスト設計コンテスト テストベース）の**逐語全文**である。本リポジトリは公開リポジトリであり、
  `AGENTS.md` の「原典の逐語転載はしない（パラフレーズのみ）」という方針に反する。
- 同じ理由で、payload JSON にも本文テキストを埋め込まない。工程Aの payload に持たせるのは
  「文書名」「対象と宣言するID」「除外するIDとその理由」だけであり、本文は実行時に `--documents-dir` から注入する。
- 工程Bの payload（`test-plan-draft.json` / `test-plan-revised.json`）はテストベースの記述を根拠に書き起こした
  テスト計画書の内容を持つが、原典の逐語転載はしない。持たせるのは ID・機能名・章節見出し・短い引用に限り、
  用語集の定義文はすべて言い換えている。
- 生成済み markdown を入力に取る工程B-2・B-3・B-5 でも、payload には本文を埋め込まず `--text-file` で注入する。
- 工程C-1の payload（`analyze-requirements.json`）も同じ方針で、01号・02号の開発背景・前提・重点項目は**すべて言い換えて**
  書き起こしている。`review-test-basis.json` は `{}` であり本文を一切持たない。
- 工程C-2の payload（`generate-user-story-map.json` / `extract-test-conditions.json`）も同じ方針で、ペルソナの4象限・
  テスト要求・テスト条件文はすべて自分の言葉で書き、原典由来の文字列は ID・機能名・画面名・章節見出しと短い語句に
  とどめている。各記述の根拠は `文書名:行番号` 形式（`09_` 0.1 と同じ表記）で示す。
- **`extract-test-conditions.json` の `requirementSources` からは `label` と `heading` を落としている。**
  `07_` 2.6 の `label` は原典該当行の**先頭最大55文字の逐語切り出し**（4.1）であり、これを payload へ写すと
  「手で書き起こす payload に逐語断片を持ち込まない」という本章の方針から外れる。`heading` は `07_` 2.6 の
  439要素すべてが `(見出しなし)` であり、`formatSourceCitation`（`src/testBasisAnalysis.ts`）が参照しないため同じく落とした。
  残したのは `requirementId` / `document` / `startLine` / `endLine` の4キーだけである。その結果、`11_` 2章の根拠位置列は
  `(11_園内チケットシステム要求仕様書, line 104-106)` のように**文書名と行番号だけ**の形式になり、原典の文字列を含まない。
  `label` を戻すと `11_` に逐語断片が入るため戻さない。
- PDF 原本は `sample/2025/2025_tdc_open_testbase/` にそのまま置かれているため、抽出物を捨てても再現性は失われない。

成果物 markdown に含まれる原典由来の文字列は、ID・機能名・章節見出し・除外理由に付した短い引用に限る。

### 4.1 工程C-1のツール出力に含まれる引用について

工程C-1のツール出力には、ツール自身が原典から切り出した短い引用が含まれる。事実として明記しておく。

- **`07_` の 2.6 要件ID → テストベース根拠位置**は、439行の表と439要素のJSONに「引用ラベル」列を持つ。
  ラベルは原典該当行の**先頭最大55文字**であり、超過分は `…` で切り詰められる（例:
  `EH-102 いますぐ入場券購入    いますぐ入場券購入に必要な機能を提供する。`）。
- **`08_` の 1.7 数量表現と3章 質問状**は、数量表現の短い断片を含む（例:「9枚まで」「2台」「30分」）。

いずれも**ツールが生成した切り詰め済みの短い引用**であり、第4章の「ID・機能名・章節見出し・短い引用に限る」という
方針の範囲内として扱う。手で編集して削ると 3.7 の `diff` が壊れるため削らない。
方針そのものを変える判断は本工程では行わない（変更が必要と判断した場合は別途 `planner` に諮る）。

### 8.1 工程D-1での実装方法

上表の6項目を工程D-1（3.15）でどう実装したかを記録する。**上表そのものは書き換えていない**。
`design_boundary_values` の `min` / `max` は「有効範囲」の宣言であるため、上限または下限の記述が2025年テストベースに
存在しない軸を変数にすると、**存在しない仕様値を成果物で主張することになる**。その3点を次のように切り分けた。

1. **残数アイコン切替閾値 `0/9/10/11` のうち、`0/9/10` は境界値変数2で列挙するが `11` は境界値では列挙しない。**
   境界値変数2は「残数僅か表示（数字1桁）となる残数」を `1〜9` と宣言しており、`0`（＝下限-刻み、「×」への切り替わり）と
   `10`（＝上限+刻み、「〇」への切り替わり）が無効側の境界として出る。一方 `11` は「〇」表示範囲の内側の値であり、
   これを境界値として出すには「〇」表示範囲の上限＝時間枠あたりの残数上限を `max` として宣言する必要がある。
   **その値は2025年テストベースに存在しない未定値である**（第7章1・第9章1。01号にあるのは「入場制限者数を倍」という
   定性的記述だけ）。したがって `11` は同値分割（変数1）の有効クラス `残数あり（〇）` の代表値 `残数11枚` として押さえ、
   境界値の `max` として捏造しない。
2. **団体予約の `30日目/31日目` は境界値ではなく同値分割（変数7）で押さえる。**
   02号:333-335 は「申込日を1日目と起算し、31日目を含むそれ以降の日付の予約購入が可能」と**下限だけを規定し、
   上限側の日数を書いていない**。これを境界値として `min: 31, max: 31` と宣言すると「32日目以降は無効」という
   テストベースに無い主張になる。同値分割の2クラス（有効 `31日目以降（受付可）` 代表値 `31日目` / 無効
   `1日目から30日目（受付不可）` 代表値 `30日目`）として宣言すれば、下限だけが確定している事実をそのまま表現できる。
   なお同じ行の「10人以上は窓口扱い」は上限が確定しているため、境界値変数6（`1〜9`）として列挙している。
3. **境界値変数3の刻み `0.1秒` と下限 `0.1` は本工程の設計判断であり、仕様由来ではない。**
   11号:1153-1154 が規定しているのは「1秒以内に入場ゲートハブから判定結果を受信しない場合は『入場不能入場券』時と
   同様のハードウェア制御を実行する」ことだけで、**待ち時間の刻みも下限も記述されていない**。仕様由来なのは
   上限 `1.0`（1秒以内は有効）だけである。`step: 0.1` を選んだのは、待ち時間を計測可能な最小単位として0.1秒を採り、
   `1.0`（有効）と `1.1`（無効）を1秒直後の境界として並べるためである。刻みを変えると `12_` の変数3の表の値が
   すべて変わるため、payload を直して 3.16 の `diff` ごと更新する。
