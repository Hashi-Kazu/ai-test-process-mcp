# 住登外者宛名番号テストベース 成果物生成手順

本書は `sample/non_contest_testbase/` 配下の成果物を **誰でも同じ入力から同じ出力に再生成できる** ようにするための手順書である。
対象はデジタル庁「地方公共団体情報システム共通機能標準仕様書」住登外者宛名番号管理機能の別紙2点
（`sample/non_contest_testbase/*.xlsx`）である。

`sample/contest_testbase/2025/` が PDF 9文書を題材にしているのに対し、本書は **Excel 2文書** を題材にする。
PDF 以外の形式でも工程A〜工程Eの全工程が通ることを実証することが目的である。

追跡: GitHub Issue #172 / Jira HSKZ-196。

---

## 2. 前提の導入

### 2.1 必要なのは Node.js のみ

**`pdftotext`（poppler-utils）は不要である。** 本テストベースはxlsx原本であり、テキスト化は
`scripts/extract-testbase-xlsx.mjs` が行う。同スクリプトは `scripts/lib/ooxml.mjs`（ZIP読み出しは `node:zlib` の
`inflateRawSync` のみ）を土台にしており、npm パッケージを追加していない。

### 2.2 MCPサーバのビルド

```bash
npm install
npm run build
```

`dist/server.js` が生成される。以降のコマンドはリポジトリルートで実行する。

### 3.1 工程共通: xlsx原本のテキスト化


**`.txt` のファイル名は原本の basename と一致させる。** `scripts/call-mcp-tool.mjs` は `--documents-dir` の

全成果物の根拠位置表記（`文書名:行番号`）になる。ファイル名昇順は
`2026-08_digital-agency_atenabango-fuban-api_spec` → `2026-08_digital-agency_atenabango-kanri_item-definition`
で決定的である。

`.work/` は `.gitignore` により除外されており、抽出テキストはコミットしない（第4章）。

### 3.2 `idPatterns` 2本（本テストベースの必須要素）

**`idPatterns` を渡さないと定義IDは0件になる。** 実測値は次のとおりである。

```bash
mkdir -p .work/rerun && echo '{}' > .work/rerun/empty.json \
&& node scripts/call-mcp-tool.mjs --tool review_test_basis \
     --payload .work/rerun/empty.json \
     --documents-dir .work/testbase/atenabango --documents-key documents \
     --out .work/rerun/no-idpatterns.md \
&& grep -n "抽出ID数" .work/rerun/no-idpatterns.md
```

```
- 対象文書数: 2 / 抽出ID数(定義 0 / 参照 1 / 目次 0) / 重複ID数: 0 / 未解決参照数: 1 / プレフィックス逸脱数: 0 / 曖昧語出現数: 47 / 数量表現数(境界語なし): 30 / ダイジェスト指摘数: 1
```

0件になる理由は2つある。

1. **データ項目IDが2セルに分割されている。** 項目定義書のデータ項目ID列は `031` と連番 `1`〜`29` が別セルに
   記録されており、抽出テキストでは `|  | 031 | 1 | 宛名番号 | …` というパイプ表行になる（item-definition:12）。
   既定パターン（`IDP-01`、プレフィックス-連番形式）はハイフン区切りのIDを前提とするため、この表記に合致しない。
2. **エラーコードが行頭にない。** エラーコード一覧の行は `| 1 |  |  |  | E0001 |  |  |  | 必須エラー | …` の形で、
   行頭に項番セルがある（fuban-api_spec:242）。`E0001` を単純に拾うパターンでは、マッチ開始位置が行頭マーカー
   直後にならないため `src/testBasisAnalysis.ts` の定義判定（`i === 0 && match.start === leadPos`）を満たさず、
   すべて参照扱いになって未解決参照になる。

そこで次の2本を、`audit_id_population` / `analyze_requirements` / `review_test_basis` の3ツールの payload へ
**同一の内容・同一の順序（P1, P2）** で渡す。正本は
`sample/non_contest_testbase/payloads/audit-id-population.json` の `idPatterns` である。

| 記号 | カタログID | 正規表現 | 役割 |
| --- | --- | --- | --- |
| P1 | `IDP-08` | `(?<![0-9A-Za-z])(\d{3})\s*\|\s*(\d{1,3})(?![0-9A-Za-z])` | 2セルに分割されたグループID＋連番を `031-1`〜`031-29` へ再構成する（2グループ） |
| P2 | `IDP-09` | `(?<=^\|\s{0,3})\d{1,3}\s*\|(?:\s*\|)*\s*(E\d{4})(?![0-9A-Za-z])` | 行頭の項番セルから match を開始させ、`E0001`〜`E0004` を定義として拾う（1グループ） |

P2 で行頭の項番セルを消費している点を変えてはならない。`(E\d{4})` だけを渡すと定義判定を満たさず、
4件すべてが未解決参照になる。2本はカタログ `testdesign://requirement-id-patterns`（`src/resources/requirementIdPatterns.ts`）
へ `IDP-08` / `IDP-09` として登録済みである。

`additionalAmbiguousTerms` / `qualityCharacteristicIds` / `perspectiveCategoryIds` は**渡さない**。
渡すと曖昧語出現数・品質特性マッピング・観点カテゴリの未使用検査の範囲が変わり、工程間で件数を直接比較できなくなる。

## 8. 読み取りの注意点（残した指摘とその根拠）

指摘を0にするために母集団を削ったり `idPatterns` を調整したりしていない。残っている指摘は次のとおりであり、
いずれも意図的に残している。

### 8.1 未解決参照2件はいずれも偽陽性である

`07_` 2.1 と `08_` 1.4 が `[high]` 未解決参照として `UTF-8` と `999-999` を検出するが、どちらも仕様欠陥ではない。

| ID | 該当箇所 | 実体 |
| --- | --- | --- |
| `UTF-8` | fuban-api_spec:163 | `Content-Type: application/json;charset=UTF-8` の文字コード指定。既定パターン（IDP-01）が `UTF` をプレフィックス、`8` を連番と解釈した |
| `999-999` | item-definition:51 | 031-24 独自施策システム等IDの行で、コード列（999）と繰り返し列（999）が隣接している。P1（IDP-08）が2セルを1つのIDへ再構成した |

**0件にするために `idPatterns` を歪めない。** P1 を `031` に限定すれば `999-999` は消えるが、
パターンの汎用性を失い、別のグループコードを持つ項目定義書へ適用できなくなる。
既定パターンから `UTF` を除く改変も副作用が大きい。偽陽性であることは `09_` SF-15 に記録している。

### 8.2 プレフィックス逸脱1件は表記の実態である

`08_` 1.5 の `[medium] digit-width-mismatch: プレフィックス「031」で連番の桁数が統一されていません。` は、
`031-1` と `031-10` のように連番が1桁と2桁で混在していることを指す。原本の表記がそうなっているため是正できない。
凡例（item-definition:79）は8桁のIDを定めているが実際の表記と一致しない。`09_` SF-11 に記録している。

### 8.3 観点カテゴリの未使用1件は対象の性質による

`11_` の未使用観点カテゴリ1件は `TPC-06 画面遷移` である。本テストベースはAPI仕様と項目定義書のみで構成され、
画面の記述が一切ないため、遷移経路・入力値の保持・ブラウザ操作のいずれもテスト条件を書けない。
`perspectiveCategoryIds` を渡して検査範囲を狭めれば0件にできるが、狭めた事実が成果物から読み取れなくなるため渡していない。

### 8.4 テスト計画書の曖昧語3件は固有名詞である

`06_` 1.4 の `「等」計3件` は、データ項目名「独自施策システム等ID」（item-definition:51）と
図形内テキストの「②住登外者宛名番号付番等」（fuban-api_spec:62）に由来する。原本の表記であり言い換えられない。
優先章での曖昧語出現数は0である。

### 8.5 `18_` の引き渡し候補2件は根拠要件IDを持たない

`18_` の「`extract_test_conditions` への引き渡し候補」に `[medium]` が2件ある。いずれもアクセストークン（DAT-01）を
運ぶ通信の遅延窓であり、経路上の通信 COM-01 / COM-03 に `requirementIds` が無いことによる。
アクセストークンは工程Aの母集団33件のどれにも対応しないため、要件IDを付けられない。
無理に別の要件IDを付けると根拠が偽になるため、そのまま残している。

### 8.6 タイムアウトと桁数不一致は合否を確定させない

タイムアウト30秒（fuban-api_spec:83）は注記で目安であると打ち消されており、確定値が存在しない。
住所_町字の桁数は項目定義書 18（item-definition:42）と付番API仕様 120（fuban-api_spec:135）で食い違う。
どちらも `12_` では両方の値を境界として設計し、`14_` では観測値を記録するにとどめ、判定はQAとして起票する。
`09_` SF-07 / SF-01 に記録している。
