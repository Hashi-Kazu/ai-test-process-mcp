## 1 はじめに

### 1.1 スコープ・目的

**スコープ:** 住登外者宛名番号付番API（app_submit/v10/jutogaishaatenabangofuban）の要求電文・応答電文と、住登外者宛名基本情報の項目定義（データ項目ID 031-1〜031-29）の整合をテスト対象とする。付番APIの入出力で設定または確認できる項目に限定し、付番APIに対応パラメータを持たない項目定義書側だけの項目（031-25 代表宛名フラグ）はテスト対象外として4章に列挙する。認可サーバによるアクセストークン発行そのもの、および基幹業務システム側の画面・帳票はテスト対象外とする。

**目的・目標:**
- 住登外者宛名番号付番APIが、処理区分 0（付番依頼）・1（既存住登外者宛名番号利用）・2（宛名番号選択情報送信）の3値それぞれで、仕様に記載された処理を行うことを確認する（fuban-api_spec:96、同:66）
- リクエストパラメータの必須指定（◎）・データ型（X / Ｎ / DATE / TIME）・データ長が、項目定義書のデータ型・桁数と矛盾しないことを、両文書の突き合わせで確認する
- HTTPステータスコード 200 / 400 / 401 / 503 の4系統それぞれについて、仕様に記載されたレスポンスオブジェクトが返却されることを確認する（fuban-api_spec:166、同:200、同:219、同:229）
- エラーコード E0001 必須エラー・E0002 指定文字エラー・E0003 桁数エラー（固定項目）・E0004 相関チェックエラーの4件が、それぞれの発生条件で返却されることを確認する（fuban-api_spec:242-245）
- 処理が30秒以上経過した場合にタイムアウトとなり、原則HTTPステータスコード500番台のエラーが返却され、JSON形式では返却されないことを確認する（fuban-api_spec:83）
- アクセストークンの検証を含むAPIアクセスから結果返却までの実行順序が、APIシーケンス図の記述どおりであることを確認する（fuban-api_spec:55-66）
- 項目定義書と付番API仕様の間で、同一のデータ項目に異なる名称または異なる桁数が与えられている箇所を、テスト実行前に仕様齟齬として洗い出す

### 1.2 背景

**現状:** 地方公共団体情報システムの統一・標準化に伴い、住登外者宛名番号管理機能は共通機能標準仕様書で規定されている。基幹業務システムは住登外者宛名番号付番APIをAPIコールして付番依頼を行い、住登外者宛名番号管理機能が住登外者宛名番号を付番して住登外者宛名基本情報を登録する。データ項目は項目定義書で29件が規定され、API側のリクエストパラメータおよびレスポンスオブジェクトと対応づけられている。

**懸念:** 項目定義書と付番API仕様は別紙として個別に管理されているため、同一のデータ項目に対する名称・データ型・桁数が両文書間で食い違うおそれがある。実際に住所_町字（item-definition:42 の Ｎ18 と fuban-api_spec:135 の Ｎ120）、氏名の外国人表記（item-definition:19 の「氏名_外国人アルファベット」と fuban-api_spec:107 の「氏名_外国人ローマ字」）、読み仮名の呼称（item-definition:25-27 の「読み仮名」と fuban-api_spec:112-114 の「フリガナ」）で不一致が確認できる。また、タイムアウト時間は「30秒以上※」と記載されつつ「目安として30秒と記載しているが、性能テストを踏まえ、適切なタイムアウト時間を設定されたい」（fuban-api_spec:83）とされており、判定に用いる確定値が定まっていない。

## 2 テスト対象

**システム概要:**
- 名称: 住登外者宛名番号管理機能（住登外者宛名番号付番API）
- 目的: 基幹業務システムからの付番依頼を受けて、自治体内で個人を一意に識別する住登外者宛名番号を付番し、住登外者宛名基本情報として登録する
- 利用者: 地方公共団体の基幹業務システム（API要求元）、住登外者宛名基本情報を登録・利用する業務の操作者
- 開発形態: 地方公共団体情報システム共通機能標準仕様書に準拠した各ベンダの実装。認可サーバは要求元認証（OAuth2.0 client_secret_jwt）を担う別構成要素
- 詳細: 通信プロトコルはHTTP1.1以上、通信セキュリティはTLS1.2以上、要求元認証はOAuth2.0 アクセストークン Bearerタイプ・認証方式 client_secret_jwt（fuban-api_spec:32-40）。本APIでサポートするHTTPメソッドはPOSTのみ（fuban-api_spec:22、同:77）。URL形式でリクエストしJSON形式で返却される（fuban-api_spec:76）。住登外者宛名基本情報のデータ項目は29件で、主キーは宛名番号（item-definition:12）

- 住登外者宛名番号付番APIコール（app_submit/v10/jutogaishaatenabangofuban、操作種類 Create）: リクエストパラメータを元に住登外者宛名番号の付番依頼を行う唯一のAPIコール（fuban-api_spec:29-30）
- 要求電文（リクエストID app_submit/v10/jutogaishaatenabangofuban_R01）: Content-Type application/json。処理区分ほか40件のパラメータ。必須（◎）は shorikubun / shikuchosonkodo / nayosemotofuragu / tagyomusanshofukafuragu / sosashaid / sosanengappi / sosajikoku（fuban-api_spec:90-155）
- 応答電文（レスポンスID app_submit/v10/jutogaishaatenabangofuban_S01）: Content-Type application/json;charset=UTF-8。正常系200は metadata / _links / result（result は shikuchosonkodo・atenabango・rirekibango・sosashaid・sosanengappi・sosajikoku）（fuban-api_spec:162-199）
- エラー応答（400 / 401 / 503）: 400 はパラメータチェックエラーで errors 配列（code / message）を返す。401 はアクセストークン無効。503 は想定外エラー（fuban-api_spec:200-238）
- エラーコード一覧（E0001〜E0004）: E0001 必須エラー、E0002 指定文字エラー、E0003 桁数エラー（固定項目）、E0004 相関チェックエラー（fuban-api_spec:242-245）
- 住登外者宛名基本情報の項目定義（031-1〜031-29）: データ型・桁数・コード・データ出力条件（必須／任意／条件付き必須）・繰り返しを規定する項目定義書。主キーは 031-1 宛名番号（item-definition:12-58）
- コード一覧（個別）_住登外者宛名番号管理: コードID 1 性別（0 不明（未記入）／1 男／2 女）、コードID 2 代表宛名フラグ（0 代表宛名／1 非代表宛名）、コードID 999 自治体固有コード（item-definition:67-72）

## 3 テスト対象機能

- 処理区分の分岐: shorikubun="0" 付番依頼（新規住登外者宛名番号を付番）、"1" 既存宛名番号利用（受信した宛名番号を住登外者宛名番号として登録）、"2" 住登外者宛名番号選択情報送信（受信した住登外者宛名番号の住登外者宛名基本情報の業務IDを更新）（fuban-api_spec:66、同:96-98）
- 必須パラメータの検査: shorikubun / shikuchosonkodo / nayosemotofuragu / tagyomusanshofukafuragu / sosashaid / sosanengappi / sosajikoku の7件が未設定の場合に E0001 必須エラーが返ること（fuban-api_spec:96-155、同:242）
- 相関必須の検査: 処理区分 "1" または "2" の場合に atenabango が必須となること、および該当時に未設定であれば E0004 相関チェックエラーが返ること（fuban-api_spec:101、同:245）

- 文字種検査: データ型 X（半角文字列）の項目に全角文字を設定した場合、データ型 Ｎ（全角文字列）の項目に規定外の文字を設定した場合に E0002 指定文字エラーが返ること（fuban-api_spec:243、item-definition:111-112）
- データ項目 031-1 宛名番号: X 15桁・必須・主キー（item-definition:12）とAPI側 atenabango X 15桁（fuban-api_spec:101）の整合

- データ項目 031-26 名寄せ先宛名番号: X 15桁・条件付き必須（名寄せ元となった宛名基本情報の場合は出力必須）（item-definition:54-55）
- データ項目 031-27〜031-29 操作系3件: 操作者ID X10、操作年月日 DATE10、操作時刻 TIME8（item-definition:56-58）とAPI側 sosashaid / sosanengappi / sosajikoku（fuban-api_spec:153-155）の整合
- データ出力条件の3区分: 必須（031-1 / 031-25 / 031-27 / 031-28 / 031-29）・任意・条件付き必須の判定と、条件付き必須の条件が項目説明に ※※ で記載されていること（item-definition:96）
- 正常系レスポンス（200）: metadata.title "住登外者宛名番号付番"・metadata.detail "登録が完了しました。"固定値・_links.self.href "/app_submit/v10/jutogaishaatenabangofuban"・result 配列の6項目（fuban-api_spec:166-199）
- エラーレスポンス（400）: title / detail "エラーが発生しました。"固定値 / _links / errors 配列（code・message）（fuban-api_spec:200-218）

- エラーレスポンス（503）: detail "想定外のエラーが発生しました。"固定値。上記以外の想定外エラーが発生した場合（fuban-api_spec:85、同:229-238）

- サービスメンテナンス時: 同様に原則HTTPステータスコード500番台のエラーが返却され、JSON形式では返却されないこと（fuban-api_spec:84）
- APIシーケンス: 1. APIアクセス w/アクセストークン → アクセストークンの検証 → ②住登外者宛名番号付番等 → 2. API結果返却 の実行順序（fuban-api_spec:55-66）
- 再実行: 正常に付番処理が実行されなかった場合に再度付番依頼を実施することにより、新規付番された番号が返却されること（fuban-api_spec:64）

## 4 テスト対象外機能

- データ項目 031-25 代表宛名フラグ: 付番APIのリクエストパラメータ（fuban-api_spec:96-155）にもレスポンスオブジェクト（同:167-199）にも対応項目が存在せず、付番API経由では値を設定も確認もできないためテスト対象外とする。APIは別項目である名寄せ元フラグ nayosemotofuragu（同:149）を持つ。項目定義書側にのみ存在する事実は仕様齟齬として別途記録する
- 認可サーバによるアクセストークンの発行処理: 本APIの要求元認証は OAuth2.0 client_secret_jwt（fuban-api_spec:37）であるが、認可サーバそのものは住登外者宛名番号管理機能の外側の構成要素であり、本仕様書はその内部処理を規定していない。アクセストークンの検証結果（有効／無効）を入力条件として扱うにとどめる
- 統一ID基盤の整備を前提とする将来の認証方式: fuban-api_spec:38 が「今後国で統一ID基盤の整備が検討されている」として暫定措置に言及しているだけで、実装対象の仕様が確定していない
- オンプレミス環境で当面認められる API Key 認証: fuban-api_spec:40 が「あくまで時限的な措置」と位置づけており、ガバメントクラウドでは原則認めないとされているため、本計画では対象としない
- 住登外者宛名番号付番API以外のAPIコール: fuban-api_spec:27-29 が提供するAPIコールを app_submit/v10/jutogaishaatenabangofuban の1件のみと定めている
- コードID 999 自治体固有コード（item-definition:72）の個々のコード値: 地方公共団体が任意に規定するコードであり、標準仕様書側で値が確定していない
- データ型 9V / S9 / BLOB / YEAR（item-definition:114-122）: 凡例に定義はあるが、住登外者宛名基本情報の29項目のいずれにも使用されていない

## 5 テスト方針

### 5.1 テストレベル

- 統合テスト: API要求元（基幹業務システム）・認可サーバ・アクセス先API（住登外者宛名番号管理機能）の3者間で、APIシーケンス図に記載された順序どおりに要求電文と応答電文がやり取りされることを確認する（fuban-api_spec:55-66）
- システムテスト: 付番依頼から住登外者宛名基本情報の登録までを通しで実行し、処理区分3値それぞれの結果が項目定義書のデータ項目に正しく反映されることを確認する
- 受け入れテスト: 地方公共団体情報システム共通機能標準仕様書への適合という観点で、リクエスト仕様・レスポンス仕様・エラーコード一覧の各記述に対する充足状況を判定する
- コンポーネントテスト: パラメータの単項目チェック（必須・データ型・桁数）は実装ベンダ側で実施済みであることを前提とし、本計画ではAPI境界からの再確認にとどめる
