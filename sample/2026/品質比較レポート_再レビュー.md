# 再レビュー: 2026年版成果物は「過去のどの成果物よりも品質が高い」か

*本書は `sample/2026/品質比較レポート.md`（2026-07-26 コミット `6a724d3` 時点）の主張を、テストベース PDF の実データおよび過去年度発表資料 10 本の全文に照らして再検証したものである。結論として、既存レポートの総括（「検証可能性・追跡可能性では過去10チームのいずれにも優る」）は**根拠が成立していない**。以下、事実関係と判定を示す。*

---

## 0 結論

**現状の 2026 年版 3 成果物は、過去のどの成果物よりも品質が高いとは言えない。** 明確に上回っていると言える過去チームは存在せず、総合で拮抗するのは Teamやま(2025)・不撓不屈(2025) の 2 チーム程度である。ミックスベジタブル(2025)・考えるアシカbeta(2025)・11ヒポポタマス(2023)・爆裂たまご(2023)には、複数の主要観点で明確に劣る。

ただしこれは MCP の到達可能性の限界ではない。サンプル生成後に追加された 6 機能（v0.12.0）が、劣後している領域のほぼすべてに対応している。問題は「MCP に機能がないこと」ではなく「サンプルが分母を絞り、決定的検査を形式的に通していること」である。

## 1 まず前提の訂正: 2025年テストベース = 2026年テストベース

既存レポートは 2023〜2025 年を一括して「過去年度」として扱っているが、実データを突き合わせると次のとおりである。

| 文書 | 2025年版 vs 2026年版 |
| --- | --- |
| 02_概要書 / 11_要求仕様書 / 12_ハードウェア仕様書 / 13_発券機画面仕様書 / 22_Web画面仕様書 / 72_データ連携仕様書 | **完全一致** |
| 01_テスト依頼書 | 版名の明示（入場システムV01→V02→V03）、誤字修正、および入場制限者数の記述精緻化のみ |
| 21_Web要求仕様書 / 71_入場券仕様書 | 版表記（Ver.1.0.0→1.0.1、©2023→©2023-2026）のみ |

つまり **2025 年決勝の 5 チーム（ふとうふくつ・考えるアシカbeta・ミックスベジタブル・ねこにサウナ・Teamやま）は、2026 年版とまったく同じ課題（入場ゲート2台増設＋入場ゲートハブ新設）を解いている。** 既存レポートはこの事実に触れておらず、直接比較の相手を「参考観点」扱いに格下げしている。

さらに 01 号文書の唯一の実質差分は次の一点である。

- 2025年版: 「入場制限者数を倍」
- 2026年版: 「入場制限者数を倍**(30分あたり30人→60人、パラメータで容易に変更可能０～999人)**」

2026 年版成果物の目玉である「0〜999 の境界値分析」は、**2025 年チームには明示されていなかった情報を与えられた上での成果**である。この点を明記せずに「境界値の厳密さで優位」と書くのはフェアではない。

## 2 既存レポートが「最大の強み」とした3点は、いずれも実データで崩れる

### 2.1 「要件ID 41件すべてカバー、未カバー0件」— 分母が実在母集団の約3割

テストベース PDF から機能ID・画面ID を実測した結果は以下のとおり。

| 文書 | 検出された定義済みID |
| --- | --- |
| 11_園内チケットシステム要求仕様書 | EH- 18件 / EG- 7件 / EK- 13件 / Z1- 5件 / Z2- 4件 = **47件** |
| 13_発券機画面仕様書 | S- **39件** |
| 21_Webチケットシステム要求仕様書 | W- **49件** / E-（エラー文言）20件 |
| 22_Webチケットシステム画面仕様書 | W- 32件（21号と重複） |

エラー文言IDを除いた機能・画面IDの実数は **約135件**。テスト分析書 2.1 節が宣言した母集団は **41件**であり、**園内チケットシステム単体の47件すら下回る**。カバレッジ「100%・未カバー0件」は、自ら 3 割に絞った分母に対する 100% である。しかも成果物中に「実在母集団に対する宣言母集団の割合」はどこにも書かれていない。

これは本 MCP の `audit_id_population`（`testbasis://population/audit-criteria`、2026-07-28 追加）がまさに検出対象としている「未宣言ID」そのものであり、サンプル生成時点（07-26）には存在しなかったツールである。

対して 11ヒポポタマス(2023) は機能（画面）一覧を全量列挙したうえで各行に「新/既存」「未/済」「優先度A〜C/NT」を付与し、対象外にも NT を明示している。ミックスベジタブル(2025) は 11 号・21 号から **316項目**の機能一覧を洗い出したうえで絞り込んでいる。母集団の扱いという一点で、2026 年版は両者に劣る。

### 2.2 「数量表現の全文書横断集約」— 30秒と60秒が抜けており、両方ともV03の中核に効く

テスト分析書 1.2 節は「秒」の検出値を **1, 2, 5, 10, 59** と記載している。テストベース全文を機械的に走査した実在値は次のとおり。

| 値 | 出典 | 意味 |
| --- | --- | --- |
| 1秒 | 11, 12, 72 | 死活監視周期／入場ゲートハブ応答タイムアウト |
| 2秒 | 12, 13 | QRコードリーダ読み取り後の無反応時間 |
| 5秒 | 12 | 入場者通過後のゲート閉 |
| 10秒 | 12 | 開後入場者通過なしのタイムアウト |
| **30秒** | **11** | **残数表示インジケータ2が時間枠別残数情報を受信する周期** |
| 59秒 | 71 | 使用可能時間の端数（29分59秒999…） |
| **60秒** | **72** | **入場管理→クラウド2 へ「使用済」入場券情報を連携するタイミング** |

**30秒と60秒が集約から欠落している。** そして欠落した2つは、いずれも V03 差分の中心リスクに直結する。

- **30秒**: 残数表示インジケータ1は 1 秒周期、インジケータ2は 30 秒周期で残数を受け取る（11号 Z2-201）。つまり両インジケータ間に最大 30 秒の表示乖離が構造的に存在する。テスト条件 TC-050「インジケータの〇表示を見て並んだら実際に購入可能であること」は、まさにこの乖離を突く条件でありながら、その発生メカニズムである 30 秒周期に本書は一言も触れていない。
- **60秒**: 72号データ連携仕様書は、状態が「使用済」に変更された入場券情報を入場管理からクラウド2へ **60秒毎**に送ると定めている。R-01（複数ゲート間QRコード整合性）と TC-060 は「使用済み状態がハブ内で即時に全ゲートへ反映されること」を期待結果としているが、Web 側への伝播には最大 60 秒の遅延がある。この 60 秒窓での挙動（Web で QR 再表示・分け与えが可能か）は、テスト条件にもケースにも一切現れていない。**V03 の最重要リスクに、テストベースに明記された数値由来の穴が残っている。**

既存レポート §3.3 はこの観点を「過去資料10件のいずれにも見当たらない独自の強み」と評価しているが、実際には**自らの掲げた基準（全文書横断・単位別の網羅集約）を満たしていない**。

### 2.3 「網羅率100%・未充足0件」— 網羅対象の紐付けが意味的に成立していない

テスト設計書 3.4 節のケース一覧で、宣言された網羅対象とケース本文の内容が対応していない箇所が複数ある。

| ケース | 宣言された網羅対象 | 実際にケースが実行する内容 |
| --- | --- | --- |
| TCS-004 | `BV:入場制限人数:0` | 入場ゲートハブ応答を1.5秒遅延させ、1秒タイムアウト時の制御を確認。入場制限人数に一切触れない |
| TCS-006 / TCS-007 / TCS-030 | `EP:残数表示状態:残数なし(×)` | いずれも障害注入（起動失敗・通信断・ACK未応答）。残数表示は登場しない |
| TCS-040 | `EP:残数表示状態:残数あり(〇)` | 8時間ソークテストの応答時間・メモリ計測。残数表示は登場しない |
| TCS-010 | `BV:入場制限人数:998, 999` | 前提条件は入場制限人数=60固定。手順は残数を10→9→1→0 と変える。998/999 には到達しない |

**「未充足の網羅対象 0件」は、意味的に無関係な網羅対象IDをケースに貼り付けることで達成されている。** 決定的層は ID の一致しか見ないため検出できず、意味的層はこれを指摘していない。既存レポート §3.1 が「機械的に提示している」と評価した数値保証は、この構造の上に乗っている。

加えて、より根の深い問題として **「入場制限人数（パラメータ、0〜999）」と「残数（時間枠ごとの残り枚数）」が同一視されている。** TCS-020 / TCS-021 / TCS-061 / TCS-063 はいずれも「対象時間枠残数 1枚」を前提とするケースだが、網羅対象は `BV:入場制限人数:1` に紐付いている。両者は別の変数であり、境界値分析は本来 2 本立てる必要がある。

### 2.4 期待結果に、テストベースに存在しない文言が引用されている

一方で参照の正確さには見るべきものがある。`S-008-01`（障害停止）、`S-001-02`（いますぐ入場券購入停止）、`S-002-02` / `S-003-04`（入場券確保失敗）、`E-020`（購入できる入場券残数がありません。）はいずれもテストベースに実在し、引用も正確である。この粒度まで実在IDで期待結果を書き下ろしている点は素直に評価できる。

ただし次の2件はテストベース中に存在しない文言である。

- TCS-061「**ご希望の枚数が確保できませんでした**」— 該当文字列なし
- TCS-011「**当日入場券購入を一時停止しています**」— 「一時停止」という語自体がテストベースに存在しない

「期待結果の主観語・空欄: 0件」という決定的検査は、こうした**実在しない文言の創作**を検出できない。検査項目としての追加余地がある。

### 重要な方法論上の留保

比較対象はいずれも **20〜38ページの発表資料**であって、成果物本体（Excel／スプレッドシート群／設計書）ではない。プレゼンに現れない詳細は評価できない。つまり「2026年版のほうが検査プロセスが可視化されている」という既存レポート §2 観点F の評価は、**成果物本体とプレゼン資料を比べたことによる見かけの優位**である可能性が高い。この留保なしに「過去10チームのいずれよりも優る」と結論するのは成立しない。

## 6 「過去のどの成果物よりも品質が高い」を実際に成立させるための手順

優先度順。1〜3 は現サンプルの欠陥修正、4〜7 は未使用機能の投入。

1. **`audit_id_population` を実行し、母集団を実在の約135件ベースへ引き直す。** 対象外とするIDは1件ずつ理由付きで宣言する。「41件中41件」ではなく「実在135件中、対象47件・除外88件（理由内訳つき）」と書けた時点で、11ヒポポタマス・ミックスベジタブルと同じ土俵に立てる。
2. **`analyze_requirements` の数量表現集約をやり直し、30秒・60秒を回収する。** とくに 72号の「使用済情報のクラウド2連携＝60秒毎」は R-01 に直結する新規テスト条件（60秒窓での Web 側 QR 再表示・分け与えの挙動）を1件以上生む。ここは過去チームも誰も突いていない領域であり、**唯一の明確な差別化点になり得る**。
3. **網羅対象の紐付けを意味整合させる。** 「入場制限人数」と「残数」で `design_boundary_values` を2本立て、fault-injection / long-run 系ケースには技法カタログに追加済みの coverageCriteria（TTK-11〜13、HSKZ-108 で追加）を使う。無関係な網羅対象IDの流用をやめれば「未充足0件」が意味を持つ。あわせて実在しない期待結果文言2件を修正する。
4. **`generate_user_story_map` ＋ 4象限ペルソナで TC-050〜054 を作り直す。** 現状の「P-01〜P-05を列挙するだけ」からねこにサウナ水準へ。
5. **`generate_exploratory_charters` でチャーターを追加する。** 11ヒポポタマス・爆裂たまごが全員やっており、ないこと自体が減点になる。
6. **`reexpand_threshold_changes` で「入場制限人数 30→60」「ゲート台数 1→3」の2スナップショットを実際に走らせ、影響再展開を成果物として出す。** 依頼書の明示要求への直接回答であり、Re:Spec への対抗手段。
7. **`review_test_basis` / `review_test_specification` を回して仕様書間の齟齬を指摘する。** 現状「曖昧語は見当たらなかった」で指摘ゼロ。ミックスベジタブルは8件指摘している。実際、22号と21号の画面遷移差分など、指摘余地は残っている。

これらを反映したうえで、はじめて「特定の観点では過去のどのチームも到達していない」と主張できる。現時点でその主張ができるのは、**強いて言えば「優先度逸脱の自己開示」と「変更差分4区分の数値重み化」の2点のみ**である。
