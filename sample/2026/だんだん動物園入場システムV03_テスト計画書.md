## 1 はじめに

### 1.1 スコープ・目的

**スコープ:** 対象: だんだん動物園入場システムのうち、園内チケットシステム(発券機、入場ゲート×3、入場ゲートハブ、入場管理、残数表示インジケータ1・2)およびWebチケットシステム(予約購入・発券・会員機能等)。特にV02→V03差分箇所(入場ゲート複数台構成・入場ゲートハブの新規追加、入場制限人数パラメータ変更(30→60、可変0～999))を最優先範囲とし、当該差分に起因するリグレッション影響を園内チケットシステム全体・入場フロー全体に対して確認する。除外: 決済システム(外部SaaS、テストエビデンス提出済みのためスコープ外)、会員登録・変更・退会機能、お問い合わせ機能、画面デザイン、QRコード生成ロジック自体(いずれも開発会社側でテスト実施済み・保証済みのため対象外。ただしこれらとの連携インタフェース自体は対象に含む)。

### 1.2 背景

**現状:** だんだん動物園入場システムは発券機・入場ゲート・入場管理からなる園内チケットシステムと、時間指定入場券をオンラインで購入できるWebチケットシステムで構成される。V01(発券機・入場ゲートのみ)からV02(時間枠制の入場者数制限、予約購入、会員機能、残数表示インジケータの追加)を経て、今回V03として以下の機能改修が行われた。(1)状況改善に伴う入場制限者数の緩和(30分あたり30人→60人、0～999人の範囲でパラメータにより容易に変更可能)、(2)人気動物により入場が捌けなくなった問題への対応として入場ゲートを2台追加(計3台)し、新たに入場ゲートハブを導入して複数ゲートでのQRコード有効/無効判定を集約する構成に変更した。だんだん市からの三密回避対策への補助金申請にあたり、追加・変更点に品質上の問題がないことを示すテスト設計成果物の提出が求められている。

**懸念:** ・各サブシステム単独で確認可能な要求事項は開発会社側で実施済み(会員登録・変更・退会、お問い合わせ、画面デザイン、QRコード作成は保証済み)。V01から差分のない箇所は運用実績により相応の信頼性があるとみなす。
・園内およびWebでの予約購入、発券、入場の流れを特に重点確認する。
・テスト重点項目: (1)システムが長時間稼働することの保証、(2)時間枠の重複販売が発生しないことの保証(制限人数超過の入場防止)、(3)密回避効果の確認(ただしこれはV01の入場ゲートでの入場記録と時間別入場者数集計機能により既に達成済みとされる)。
・V02→V03の差分、特に入場ゲート台数増加・入場ゲートハブ新設に伴うリグレッションテストと、今後の変更に備えた回帰テスト観点の提案が求められている。

### 1.4 前提条件・制約

**前提条件:**
- 会員登録・変更・退会、お問い合わせ、画面デザイン、QRコード生成ロジックは開発会社側で保証済みであり、本テストでは連携インタフェースのみを確認対象とする
- V01からV02・V03を通じて変更のない箇所(発券機の決済処理等)は運用実績により十分な信頼性が確保されているとみなす
- 決済システムはスコープ外だが、決済結果を受けた園内チケットシステム側の後続処理(発券・エラーハンドリング)はテスト対象に含む

**制限事項:**
- 決済システムは外部SaaSでありテスト環境での自由な障害注入が制限される可能性があるため、スタブ/シミュレータでの代替を前提とする
- 入場ゲート実機3台・入場ゲートハブを用いた同時アクセステストには相応の物理的テスト環境(実機または模擬環境)が必要

## 2 テスト対象

**システム概要:**
- 名称: だんだん動物園入場システム(入場システムV03)
- 目的: 入場者数を時間枠単位で制限しつつ、発券機およびWebでの入場券の予約購入・当日購入・発券・入場をペーパーレスも含め可能にする。三密回避と入場ゲート付近の滞留リスク低減を両立する。
- 利用者: だんだん動物園の来園者(入場者、Web会員/ゲスト)、だんだん動物園の運用担当者(事務所からの機器監視・予約管理)
- 開発形態: 既存システム(入場システムV02)に対する追加改修。園内チケットシステム側は「だんだん開発」、Webチケットシステム側は「DEAN2開発」がそれぞれ別会社で開発。決済システムは外部決済サービス会社のSaaSを利用。
- 詳細: 構成: 園内チケットシステム(発券機×3、入場ゲート×3、入場ゲートハブ、残数表示インジケータ1・2、入場管理)、Webチケットシステム(メールサーバ、Web/Appサーバ、ロードバランサ、VPN-GW、予約管理DBサーバ、会員情報管理DBサーバ)、決済システム(外部SaaS、スコープ外)。V02→V03差分: 入場ゲート2台追加(計3台)、入場ゲートハブ新設(各入場ゲートからのQRコード読み取り結果を集約しQRコード有効/無効判定を実施)、入場制限者数を30分あたり30人→60人に緩和(0～999人の範囲でパラメータ変更可能)。

- 入場ゲート複数台(3台)構成の入場処理: 入場ゲートハブ経由でのQRコード有効/無効判定、複数ゲート同時読み取り時の排他制御、使用済みQRコードの即時無効化がゲート間で正しく反映されるか
- 入場ゲートハブ機能: 入場券情報一覧の取得・同期(起動時、新時間枠開始時、いますぐ入場券購入契機の更新時)、QRコード有効/無効判定応答、入場管理との死活監視ACK応答
- 入場制限人数パラメータ変更(30→60人、可変0～999人): 時間枠あたりの残数管理・残数表示・購入可否判定・残数アイコン切替閾値が変更後パラメータに基づき正しく動作するか、境界値(0人、999人、1人)での挙動
- 発券機での購入・発券: いますぐ入場券購入、時間指定入場券購入(会員ログイン有無)、予約済み入場券発券、各種支払い方法(現金・カード・QRコード決済・非接触電子マネー)
- Webチケットシステムでの予約購入・発券: 時間帯指定予約購入、支払い方法選択、QRコード表示・印刷プレビュー、入場券分け与え(メール送信)
- 残数表示インジケータ1・2: 入場管理からの残数配信を受けた表示切替(〇/△/数字/×)、閾値変更後の表示挙動、通信障害時のブランク表示
- 入場管理の時間枠別残数更新処理: 購入時の減算・購入中止時の加算処理の整合性、時間枠重複販売防止(同時購入の排他制御)
- システム死活監視・障害時停止: 発券機・入場ゲート・入場ゲートハブ・Webチケットシステム側各構成要素の3回連続ACK未応答時の障害検知、障害停止画面遷移
- 長時間稼働: 開園(10:00)～閉園(18:00)相当の連続稼働において、購入・発券・入場処理が安定して継続できること

## 3 テスト対象機能

- 入場ゲート3台構成でのQRコード読み取り・入場可否判定・ゲート開閉制御(ハードウェア仕様書準拠)
- 入場ゲートハブの入場券情報一覧同期タイミング(起動時/毎時00分・30分/いますぐ入場券購入時)

- 入場制限人数パラメータ変更時の残数表示・購入可否・残数アイコン切替閾値への反映(0～999人の境界値)
- 発券機でのいますぐ入場券購入・時間指定入場券購入・予約済み入場券発券の一連のフロー
- 発券機の各支払い方法(現金/カード/QRコード決済/非接触電子マネー)とエラー時(残高不足・カードNG等)の挙動
- Webチケットシステムでの新規登録・ログイン・予約購入・支払い・QRコード表示/印刷プレビュー・入場券分け与えの一連のフロー

- 入場管理・入場ゲートハブ・発券機間の死活監視によるシステム障害検知と障害停止画面表示
- 会員情報と発券機/Webチケットシステム双方での予約購入・発券の紐づけ(再発券含む)
- 長時間稼働時のメモリリーク・処理遅延・応答timeout(入場ゲートハブの1秒以内応答等)の有無

## 5 テスト方針

### 5.1 テストレベル

- システムテスト(結合された園内チケットシステム・Webチケットシステム全体を対象とした機能・シナリオテスト)
- リグレッションテスト(V02→V03差分に起因する影響範囲、特に入場ゲート・入場ゲートハブ・残数表示関連の回帰確認)

### 5.2 テストタイプ

| 対象 | テストタイプ | 説明 |
| --- | --- | --- |
| ○ | 機能テスト | 機能が期待どおりの結果を返すか確かめる |
| ○ | シナリオテスト | 実際の利用手順に沿って操作し利用できるか確かめる |
| ○ | 性能テスト | 処理時間などパフォーマンスを測定する。長時間稼働時の応答性能、入場ゲートハブの1秒以内応答を対象とする |
| ○ | ロードテスト | 様々な状況で動作させ期待どおりか確かめる。複数発券機・複数入場ゲートからの同時アクセスを対象とする |
| ○ | ストレステスト | 限界もしくはそれ以上の負荷を与え動作を確かめる。同時購入による限界負荷、時間枠重複販売防止の限界確認を対象とする |
| — | ユーザビリティテスト | 理解されやすく使いやすく魅力的か確かめる(画面デザインは開発会社にて保証済みのため対象外) |
| — | ローカライゼーションテスト | 異なる言語に変換されても機能するか確認する(システム全体の対応言語は日本語のみのため対象外) |
| — | 保守性テスト | 欠陥修正や機能追加のしやすさを確かめる(本テストのスコープ外) |
| ○ | 信頼性テスト | 要件で決めた回数・期間・条件で稼働できるか確かめる。開園～閉園相当時間のソークテストを対象とする |
| — | 移植性テスト | 別ハード・環境への移植のしやすさを確かめる(専用ハードウェア機器のためスコープ外) |

### 5.3 テスト技法

| テストタイプ | アプローチ | 技法 |
| --- | --- | --- |
| 入場制限人数パラメータ(0～999人) | 0人、1人、998人、999人、現行値相当(60人)の境界および代表値で残数表示・購入可否・閾値切替を確認する | 境界値分析・同値分割 |
| 時間枠重複販売防止 | 複数発券機およびWebチケットシステムから同一時間枠へ同時に購入要求を発生させ、残数を超える販売が発生しないことを確認する | 並行処理・競合状態テスト |
| 入場ゲート3台構成でのQRコード判定 | 複数ゲートでの同時読み取り、使用済みQRコードの他ゲートでの再利用試行、入場ゲートハブ障害時の全ゲート挙動を組み合わせて確認する | 組み合わせテスト・状態遷移テスト |
| 発券機・Webチケットシステムの入力項目 | 購入枚数(1～9枚)、支払い方法の正常/異常系、券種(おとな/こども)の組み合わせをデシジョンテーブルで整理し検証する | 同値分割・境界値分析・デシジョンテーブル |
| 長時間稼働 | 開園から閉園相当の時間、継続的に購入・発券・入場処理を発生させ続け、性能劣化や異常終了がないことを確認する | ソークテスト(耐久テスト) |
| システム障害検知・死活監視 | 発券機・入場ゲート・入場ゲートハブ・Webチケットシステム側構成要素を意図的に停止させ、3回連続ACK未応答による障害検知と障害停止画面遷移が仕様通り行われるか確認する | 障害注入テスト |

## 6 合否基準

### 6.1 開始・終了基準

**開始基準:** 対象範囲(V02→V03差分含む)のテスト対象成果物(発券機・入場ゲート・入場ゲートハブ・入場管理・残数表示インジケータ・Webチケットシステム)が結合された状態でテスト環境に構築されていること。関連仕様書(要求仕様書、画面仕様書、ハードウェア仕様書、入場券仕様書、データ連携仕様書)が最新版で入手可能であること。テストデータ・テスト環境(決済システムのスタブ/シミュレータ含む)の準備が完了していること。

**終了基準:** 計画した全テストケースが実施され、テスト重点項目(長時間稼働の安定性、時間枠重複販売防止、密回避効果の維持)に関する検証が完了していること。6.4のインシデントランクに基づき、ランクA(致命的)・ランクB(重大)の不具合が0件であること(ランクC以下は是正計画に合意し課題管理台帳へ記録済みであること)。

### 6.2 合否判定基準

各テスト項目は、実施結果(実際の結果)が期待結果と一致した場合に合格(OK)と判定する。実施結果に差異があり、その原因が6.4のインシデントランクでランクAまたはランクBに該当する不具合の場合は当該テスト項目を不合格(NG)とする。ランクCまたはランクDに該当する軽微な差異については、テスト項目自体は合格(OK)としつつ、当該インシデントを課題管理台帳に記録し、是正計画についてステークホルダーの合意を得るものとする。テスト全体の合否は、計画した全テスト項目のうち不合格(NG)が残存しないこと、かつランクA・ランクBの不具合が0件であることをもって判定する。

**判定ステータス定義:**

| ステータス | 説明 |
| --- | --- |
| OK | 問題なくテストが完了した項目 |
| NG | インシデントが検出された項目 |
| QA | QA表で質問中の項目 |
| NT | テストを実施しない項目（同義：テスト対象外） |
| N/A | テスト実施ができない項目（同義：不可・機能削除・Drop等） |
| 保留 | 最終的には実施可能だが現状は何らかの事情で実施できない項目 |

### 6.3 完了基準

- 設計した全テストケースの実施完了(実施率100%)
- 致命的(Critical/High)不具合の修正確認完了
- 時間枠重複販売が発生しないことの確認完了
- 長時間稼働(開園～閉園相当時間)におけるシステム異常が発生しないことの確認完了

### 6.4 インシデント判定基準

| ランク | 説明 |
| --- | --- |
| ランクA | 基本操作で機能が正常に動作しない／仕様・マニュアルと異なる動作／ユーザーが回避操作不能（フリーズ・リセット等） |
| ランクB | ある条件で正常に動作しない／通常想定される性能を大きく下回る／ユーザーが回避操作可能 |
| ランクC | 特殊条件で機能が正常に動作しない／性能をやや下回る／仕様と区別がつかない |
| ランクD | 機能・性能・表示系への要望や改良提案 |

### 6.5 質問事項重要度基準

| 重要度 | 説明 |
| --- | --- |

| 中 | テストは続行できるが回答が必要（未回答が○件以上） |

## 7 中断・再開基準

**中断基準:** 以下のいずれかに該当する場合、テストを中断する。
- 決済システムのスタブ/シミュレータが応答不能となり、支払い処理を含むテスト項目の続行が不可能な場合
- 入場ゲート実機または入場ゲートハブに物理的な故障が発生し、当該機器を用いるテスト項目の続行が不可能な場合
- ランクA(致命的)の不具合により、テスト対象システムの以降のテスト項目が実施不能な場合

**再開基準:** 上記の中断原因が解消され、環境復旧確認(主要な購入・発券・入場フローが一通り動作することを確認するスモークテスト相当の再疎通確認)が完了した場合にテストを再開する。

## 14 リスク・対策

### 14.1 プロダクトリスク

- 入場ゲート3台+入場ゲートハブという新規構成により、複数ゲート間での使用済みQRコードの整合性が崩れ、同一QRコードで複数ゲートから入場できてしまう (影響: high) — 対策: 入場ゲートハブでのQRコード状態(未使用/使用済/無効)更新と複数ゲートへの反映タイミングを重点的にテストし、競合シナリオを網羅する
- 入場制限人数パラメータを0～999人の範囲で自由に変更可能にしたことで、極端な値(0人、999人)や変更直後のタイミングで残数表示・購入可否判定に不整合が生じる (影響: medium) — 対策: 境界値分析によるパラメータ変更テストを実施し、変更直後の既存予約への影響も確認する
- 入場ゲート台数増加および入場ゲートハブ追加によりゲート付近の同時アクセスが増加し、応答遅延やゲート開閉のタイムアウト(1秒以内判定)が発生する (影響: medium) — 対策: 複数ゲート同時読み取りを想定した負荷・並行処理テストを実施する
- 決済システムがスコープ外であることにより、決済システムとの通信障害時の園内チケットシステム側のフォールバック処理(障害停止画面表示等)が十分検証されない (影響: low) — 対策: 決済システムのスタブ/シミュレータを用いて通信障害パターンを模擬したテストを実施する

### 14.2 プロジェクトリスク

- 園内チケットシステム(だんだん開発)とWebチケットシステム(DEAN2開発)が別会社で開発されているため、結合テストで検出した連携不具合の原因切り分けおよび修正対応の調整に時間を要し、テストスケジュールが遅延する (影響: medium) — 対策: テストリーダーが両開発会社との連絡窓口を一本化し、結合テスト開始前に連携インタフェース仕様の齟齬がないことを事前確認する
- 決済システムが外部SaaSであることにより、テスト環境での障害注入シナリオ(通信断・タイムアウト等)の実施可否・実施タイミングが決済サービス会社側の都合に左右され、計画通りにテストが進められない (影響: low) — 対策: 決済システムのスタブ/シミュレータを主体に利用し、実機連携での障害注入は早期に日程調整を行う
