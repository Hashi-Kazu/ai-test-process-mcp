### 1.2 採用した網羅基準

- 工程Aで確定した宣言母集団109件（`sample/contest_testbase/2025/01_ID母集団監査_2025テストベース.md` 2.8 の「宣言済み 109」）のすべてに、紐づくテスト条件が1件以上ある。
- テストベース／ステークホルダー／リスク／ガイドワードの4系統すべてから条件を導出している。
- テスト観点カタログの `TPC-01`〜`TPC-18` の18カテゴリすべてを1件以上使用している（`perspectiveCategoryIds` で対象カテゴリを絞らない）。
- リスク分析フレームの `RC-01`〜`RC-05` の5区分すべてを、リスクまたはテスト条件のいずれかで検討している。
- すべてのテスト条件の根拠位置が、`sample/contest_testbase/2025/07_要件分析結果_2025テストベース.md` 2.6 の要件ID→根拠位置対応、または明示した `sourceRefs` で特定済みである。
- `sample/contest_testbase/2025/09_テストベース仕様齟齬指摘_2025テストベース.md` の `SF-09` の60秒窓をリスク・ステークホルダー・ガイドワードの3系統から3件以上のテスト条件として導出し、`SF-05` / `SF-06` / `SF-07` / `SF-08` / `SF-10` も条件化している。
- `sample/contest_testbase/2025/10_利用状況モデリング結果.md` 5節のテスト要求 `TR-01`〜`TR-14` を、ペルソナ `P-01`〜`P-05` から導出した条件の `rationale` から参照し、テスト要求からテスト条件への追跡を切らさない。
- 条件IDは `TC-001` からゼロ埋め3桁で欠番なく連続し、すべての条件に優先度・影響度・発生可能性・変更区分を付与している。

### 1.3 導出系統(source)の定義

| source | 名称 | 説明 |
| --- | --- | --- |
| testbase | テストベース由来 | 要件・仕様の記述そのものから導出した条件。derivedFrom には要件IDを書く。 |
| stakeholder | ステークホルダー由来 | 利用者・運用者などの関心事から導出した条件。derivedFrom にはペルソナIDを書く。 |
| risk | リスク由来 | 洗い出したリスクから導出した条件。derivedFrom にはリスクIDを書く。 |
| guideword | ガイドワード由来 | 着目点×ガイドワードの掛け合わせで見つけた条件。derivedFrom には着想元の要件ID/リスクID/ペルソナIDを書く。複数系統にまたがる場合は `{kind, id}` 形式で種別を明示できる。 |

source と derivedFrom は必須メタデータであり、どちらも空にしてはならない。

## 4. 採用した優先度基準

### 4.1 リスクレベル算出式

riskScore = impact(1..5) × likelihood(1..5) × changeWeight(1..3)（範囲 1..75）。changeWeight は変更差分軸の value を用い、changeCategory 未指定時は 2 を既定とする。

#### RA-IMPACT 影響度

その不具合が起きたときに業務・利用者・事業へ与える打撃の大きさ。

| 値 | レベル | 判定基準 |
| --- | --- | --- |
| 1 | 影響ほぼなし | 気付かれない程度の軽微な差異で、業務も利用者も影響を受けない。 |
| 2 | 軽微（回避策あり） | 不便はあるが、簡単な回避策で業務を続けられる。 |
| 3 | 業務に支障（手作業で復旧可） | 業務が滞るが、手作業や再実行で復旧できる。 |
| 4 | 重大（業務停止・データ不整合） | 業務が停止するか、データ不整合が生じて修復に手間がかかる。 |
| 5 | 致命的（金銭損失・法令違反・個人情報漏洩） | 金銭的損失、法令違反、個人情報の漏洩など、組織の信用に直結する。 |

#### RA-LIKELIHOOD 発生可能性

実運用の中でその事象がどの程度の頻度で起こり得るか。

| 値 | レベル | 判定基準 |
| --- | --- | --- |
| 1 | ほぼ起きない | 特殊な条件が重ならないと発生しない。 |
| 2 | まれ | 年に数回程度、限られた利用者だけが遭遇する。 |
| 3 | ときどき | 月に数回程度、通常運用の中で遭遇し得る。 |
| 4 | 頻繁 | 日常的に利用される経路で高い頻度で遭遇する。 |
| 5 | 常に起こりうる | 主要な操作経路上にあり、ほぼ全利用者が遭遇する。 |

#### RA-CHANGE 変更差分

対象が今回の変更でどれだけ手を入れられたか（analyze_requirements の4区分に対応）。

| 値 | レベル | 判定基準 |
| --- | --- | --- |
| 1 | existing-unaffected（既存・影響なし） | 今回の変更で手が入らず、影響も受けないと判断できる範囲。 |
| 2 | existing-impacted（既存・影響あり） | 直接は変更していないが、共通部品や共有データを介して影響を受ける範囲。 |
| 3 | modified（変更） | 既存の実装に手を入れた範囲。 |
| 3 | new（新規実装） | 今回新たに作られ、実績のない範囲。 |

changeCategory が未指定の場合、changeWeight は既定値 2 として計算する。

### 4.2 リスクスコア → 優先度の写像

| リスクレベル | スコア範囲 | 優先度 | 指針 |
| --- | --- | --- | --- |
| R1 | 30..75 | 高 | 最優先で条件を詳細化し、複数技法で厚めに設計する。 |
| R2 | 15..29 | 中 | 代表的な条件を確実に押さえ、境界・異常系を1件以上含める。 |
| R3 | 6..14 | 低 | 代表条件のみに絞り、工数が不足する場合は縮小候補とする。 |
| R4 | 1..5 | 低 | 実施対象外候補。除外してよいか関係者と要相談のうえ判断する。 |

### 4.3 宣言された優先度基準

- 優先度は 4.1 のリスクスコア算出式（影響度 × 発生可能性 × 変更差分の重み）から導出した値をそのまま宣言し、導出優先度との逸脱を作らない。
- 変更差分は、入場ゲートハブとWebチケットシステムの新規範囲を `new`、11号 Ver.1.1.0 で記載が変更された入場ゲート・入場管理・残数表示インジケータを `modified`、発券機の既存機能を `existing-impacted`、工程Aで対象外に宣言した処理へ隣接する選択分岐を `existing-unaffected` として割り当てる。
- 影響度と発生可能性はすべてのテスト条件に付与し、リスク未算出を0件にする。
- 時間枠あたりの入場制限者数（`09_` SF-13）と入場ゲートの総台数（`09_` SF-14）は未定値として扱い、これらを前提に優先度を引き上げることはしない。

## 6. 観点カタログによる追加観点の洗い出し指示(意味的層)

以下のカテゴリごとに、対象要件に該当するテスト条件が漏れていないか検討し、不足があれば source と derivedFrom を付けて追加すること。3.3 で未使用と判定されたカテゴリを優先的に検討すること。

### TPC-01 機能

要件に記載された機能そのものが意図どおりに実現できているかを確かめる観点。

- TPC-01-01 主要機能の実現: 要件記載の機能が単体で意図どおり動くか / 操作の入口と出口が揃っているか / 機能を使い切るまでの一連の手順が途切れずに完了できるか(推奨技法: scenario-based, decision-table, checklist-based)
- TPC-01-02 計算・判定ロジック: 計算結果が仕様値と一致するか / 端数処理・丸めの方向が仕様どおりか / 判定条件の組み合わせごとに正しい結果が返るか(推奨技法: decision-table, boundary-value-analysis, checklist-based)
- TPC-01-03 機能間の整合: 同じ情報を扱う複数機能で結果が一致するか / 一方の機能での更新が他方の表示に正しく反映されるか(推奨技法: scenario-based, checklist-based)

### TPC-02 正常系・準正常系・異常系

経路の種類を正常・準正常・異常に分け、どの経路も想定どおり扱われるかを確かめる観点。

- TPC-02-01 正常系: 想定操作・想定データでの成功経路が完了するか / 成功時の結果表示・後続処理が仕様どおりか(推奨技法: scenario-based, equivalence-partitioning)
- TPC-02-02 準正常系: キャンセル・差戻し・再入力で状態が破綻しないか / 部分入力のまま中断した場合の扱いが決まっているか(推奨技法: scenario-based, decision-table)
- TPC-02-03 異常系: 不正入力・必須未入力に対する拒否とメッセージが適切か / 権限不足・システムエラー時の振る舞いとメッセージが適切か(推奨技法: equivalence-partitioning, decision-table, error-guessing)

### TPC-03 境界

値・件数・桁数の境界付近で判定が切り替わる箇所を確かめる観点。

- TPC-03-01 数値・日付の境界: 上限・下限とその直前直後で判定が切り替わるか / 境界を含む/含まないの扱いが仕様どおりか / 年度末・月末・うるう日で日付計算が破綻しないか(推奨技法: boundary-value-analysis)
- TPC-03-02 桁数・件数の境界: 最小文字数・最大文字数とその直前直後で扱いが変わるか / 0件・1件・最大件数での一覧表示や集計が正しいか(推奨技法: boundary-value-analysis)

### TPC-04 同値

入力を同じ扱いになるグループへ分け、各グループの代表値で確かめる観点。

- TPC-04-01 有効同値クラス: 区分ごとの代表値で期待どおりの処理が行われるか / 同じ区分内の別の値でも結果が変わらないか(推奨技法: equivalence-partitioning)
- TPC-04-02 無効同値クラス: 型違い・範囲外・空文字での拒否が一貫しているか / 記号・全角半角混在の入力が想定どおり扱われるか(推奨技法: equivalence-partitioning, error-guessing)

### TPC-05 状態遷移

業務上の状態と遷移を洗い出し、許される遷移と許されない遷移を確かめる観点。

- TPC-05-01 正当な遷移: 全状態・全遷移を一度は通過できるか / 遷移の前後で関連データが整合するか(推奨技法: state-transition)
- TPC-05-02 不正な遷移: 起こり得ない遷移要求が確実に拒否されるか / 拒否時のメッセージと状態の巻き戻しが適切か(推奨技法: state-transition, error-guessing)
- TPC-05-03 状態の永続化: 中断・再開後も状態が保たれるか / セッション切断や再ログイン後に状態が失われないか(推奨技法: state-transition, scenario-based)

### TPC-06 画面遷移

画面間の移動と入力値の引き継ぎ、ブラウザ操作への耐性を確かめる観点。

- TPC-06-01 遷移経路: 正順の遷移と戻り操作の両方で正しい画面へ移動するか / 直リンクでの到達時に前提チェックが働くか(推奨技法: state-transition, scenario-based)
- TPC-06-02 入力値の保持: 遷移前後で入力値・選択状態が保持されるか / スクロール位置やページングの位置が失われないか(推奨技法: scenario-based)
- TPC-06-03 ブラウザ操作: 戻る/進む/更新の操作後も画面と状態が一致するか / 多重タブで同じ画面を開いた場合に不整合が起きないか(推奨技法: state-transition, exploratory)

### TPC-07 並行・競合

同時実行や同時更新で発生する競合とロックの扱いを確かめる観点。

- TPC-07-01 同一データの同時更新: 後勝ち・排他・競合検知のいずれの方針か明確で、そのとおり動くか / 競合が検知された際の利用者への提示と復旧手段が用意されているか(推奨技法: concurrency-test)
- TPC-07-02 多重実行: 多重ログインが許されるか、許す場合の影響が把握されているか / 二重送信で二重登録が発生しないか(推奨技法: concurrency-test, error-guessing)
- TPC-07-03 ロック: ロック待ちが過度に長くならないか / デッドロックが発生した場合に検知・解消できるか(推奨技法: concurrency-test, load-test)

### TPC-08 タイミング・順序

処理の順序・時刻依存・タイムアウトの境界を確かめる観点。

- TPC-08-01 処理順序: 前提処理が未完了のまま後続を実行した場合の振る舞いが決まっているか / 非同期処理の完了順が入れ替わっても結果が壊れないか(推奨技法: timing-order-test, state-transition)
- TPC-08-02 時刻依存: 締め時刻の直前直後で扱いが切り替わるか / 日付変更・営業時間外での操作が仕様どおり扱われるか(推奨技法: timing-order-test, boundary-value-analysis)
- TPC-08-03 タイムアウト: 通信・セッション・操作の各タイムアウト境界で挙動が仕様どおりか / タイムアウト後の再操作でデータが二重に登録されないか(推奨技法: timing-order-test, boundary-value-analysis)

### TPC-09 データライフサイクル

データの生成から廃棄・移行までの各段階と関連データへの波及を確かめる観点。

- TPC-09-01 生成〜更新〜削除: 各段階でデータの整合が保たれるか / 関連データへの波及（親子・集計値）が正しく行われるか(推奨技法: data-lifecycle-test, state-transition)
- TPC-09-02 論理削除・物理削除: 削除済みデータが一覧・検索・帳票から除外されるか / 復元が必要な場合に復元手段と範囲が定義されているか(推奨技法: data-lifecycle-test)
- TPC-09-03 保持期間・アーカイブ: 保持期限の到来時に自動処理が仕様どおり動くか / アーカイブ済みデータの参照可否が明確か(推奨技法: data-lifecycle-test, boundary-value-analysis)
- TPC-09-04 移行・旧仕様データの扱い: 旧仕様で作られたデータが新仕様で正しく解釈されるか / 移行データの欠落・重複・文字化けが起きないか(推奨技法: data-lifecycle-test, regression-selection)

### TPC-10 構成・環境

利用環境や設定値の組み合わせによる差異を確かめる観点。

- TPC-10-01 端末・OS・ブラウザの組み合わせ: 対象として宣言された環境すべてで主要機能が動作するか / 環境固有の表示崩れや操作不能が起きないか(推奨技法: config-matrix, pairwise)
- TPC-10-02 画面サイズ・解像度・拡大率: 小さい画面幅で要素が重ならず操作できるか / 文字拡大時にラベルやボタンが欠けないか(推奨技法: config-matrix)
- TPC-10-03 ネットワーク条件: 低速・不安定な回線で操作が完了できるか / オフライン時の表示と再接続後の復帰が適切か(推奨技法: config-matrix, fault-injection)
- TPC-10-04 設定値・パラメータの組み合わせ: 設定値の組み合わせで矛盾する挙動が起きないか / 既定値のまま利用した場合に問題が生じないか(推奨技法: config-matrix, pairwise)

### TPC-11 障害・縮退・回復

障害発生時の振る舞い、縮退運転、復旧手順を確かめる観点。

- TPC-11-01 外部システム障害: 応答なし・エラー応答・不正応答のそれぞれで適切に処理されるか / 障害を利用者へ伝えるメッセージが分かりやすいか(推奨技法: fault-injection)
- TPC-11-02 処理中断: 通信断やプロセス停止の後でデータ整合が保たれるか / 中途半端な状態が残った場合に検知・修復できるか(推奨技法: fault-injection)
- TPC-11-03 リトライと冪等性: 再送で二重登録・二重課金が起きないか / リトライ回数・間隔が仕様どおりか(推奨技法: fault-injection, concurrency-test)
- TPC-11-04 縮退運転・復旧手順: 一部機能停止時にも業務継続に必要な機能が使えるか / 手順書どおりの操作で想定時間内に復旧できるか(推奨技法: fault-injection, checklist-based)

### TPC-12 長時間稼働

長期間の連続稼働で徐々に現れる劣化や累積の問題を確かめる観点。

- TPC-12-01 資源の単調増加: メモリ・ディスク使用量が時間とともに増え続けないか / コネクションやファイルハンドルが解放されるか(推奨技法: long-run-test)
- TPC-12-02 累積データ量に伴う性能劣化: データが積み上がった状態でも応答時間が許容範囲か / 一覧・検索・集計が実運用相当のデータ量で完了するか(推奨技法: long-run-test, load-test)
- TPC-12-03 日跨ぎ・週跨ぎの定期処理: 日付が変わっても定期処理が欠落・重複しないか / 連続稼働中の定期処理が前回結果に影響されないか(推奨技法: long-run-test, timing-order-test)

### TPC-13 性能・負荷

応答時間・処理量・限界超過時の振る舞いを確かめる観点。

- TPC-13-01 応答時間: 代表操作の応答時間が目標値を満たすか / 遅い操作について進行状況が利用者に示されるか(推奨技法: load-test)
- TPC-13-02 スループット・同時利用者数: 想定同時利用者数で処理量が目標を満たすか / 同時実行数を上げたときの劣化の仕方が緩やかか(推奨技法: load-test, concurrency-test)
- TPC-13-03 ピーク負荷と限界超過: ピーク時想定の負荷で業務が完遂できるか / 限界を超えた場合に安全側で縮退・拒否できるか(推奨技法: load-test, fault-injection)

### TPC-14 運用・保守

稼働後の運用作業や障害調査に必要な仕組みを確かめる観点。

- TPC-14-01 ログ・監査証跡: 誰が何をしたかを追跡できる形でログが残るか / 調査に必要な情報が欠けていないか(推奨技法: checklist-based)
- TPC-14-02 監視・通知: 異常を検知して通知が到達するか / 通知の内容から一次対応の判断ができるか(推奨技法: checklist-based, fault-injection)
- TPC-14-03 バッチ・定期処理: 実行・再実行の手順が定義され、そのとおり動くか / 失敗時の扱い（中断・スキップ・リカバリ）が明確か(推奨技法: checklist-based, timing-order-test)
- TPC-14-04 バックアップ・リストア: 取得したバックアップから実際に復元できるか / 復元後のデータ範囲と欠損時間が想定どおりか(推奨技法: checklist-based, data-lifecycle-test)

### TPC-15 セキュリティ

認証・認可・入力検証・機密情報の扱いを確かめる観点。

- TPC-15-01 認証: ログイン失敗時のロックアウトとパスワード規則が仕様どおりか / セッションの有効期限と再認証が機能するか(推奨技法: checklist-based, boundary-value-analysis)
- TPC-15-02 認可: 権限別に可視範囲・操作可能範囲が制限されるか / 直接URLアクセスや他人データの参照が拒否されるか(推奨技法: checklist-based, decision-table)
- TPC-15-03 入力検証: 不正文字列の混入が拒否またはエスケープされるか / サーバ側でも検証が行われるか(推奨技法: checklist-based, error-guessing)
- TPC-15-04 機密情報の扱い: 通信・保存時に適切に保護されているか / ログや画面表示でマスキングされるか(推奨技法: checklist-based)

### TPC-16 ユーザビリティ・アクセシビリティ

利用者が迷わず操作でき、支援技術でも利用できるかを確かめる観点。

- TPC-16-01 操作導線とエラーメッセージの理解性: 初見の利用者が次に何をすべきか分かるか / エラーメッセージから原因と対処が読み取れるか(推奨技法: checklist-based, exploratory)
- TPC-16-02 キーボード操作・フォーカス順序: マウスを使わずに主要操作を完了できるか / フォーカス順序が画面の意味的な順序と一致するか(推奨技法: checklist-based, exploratory)
- TPC-16-03 支援技術での利用: 読み上げで画面の意味が伝わるか / 画像の代替テキストと文字色のコントラストが確保されているか(推奨技法: checklist-based)

### TPC-17 ローカライズ

言語・書式・文字コードの違いによる問題を確かめる観点。

- TPC-17-01 言語・文言: 未翻訳の文言が残っていないか / 翻訳による文字数増加でレイアウトが崩れないか(推奨技法: config-matrix, checklist-based)
- TPC-17-02 日時・数値・通貨の書式: 地域ごとの書式で表示・入力できるか / タイムゾーン差で日付がずれないか(推奨技法: config-matrix, boundary-value-analysis)
- TPC-17-03 文字コード・多言語文字: 絵文字・サロゲートペア・結合文字が保存・表示できるか / 文字数カウントが仕様どおりの単位で行われるか(推奨技法: boundary-value-analysis, equivalence-partitioning)

### TPC-18 リグレッション

変更によって既存の保証範囲が壊れていないかを確かめる観点。

- TPC-18-01 変更影響範囲: 変更差分から影響を受ける既存機能が特定されているか / 影響範囲の既存機能が変更後も動作するか(推奨技法: regression-selection)
- TPC-18-02 既存保証範囲の再確認: 過去に発生した不具合が再発していないか / 従来の主要業務シナリオが引き続き完遂できるか(推奨技法: regression-selection, scenario-based)
- TPC-18-03 共通部品・共有データの利用箇所: 変更した共通部品を使う全画面・全機能が確認されているか / 共有マスタ・共有設定の変更が想定外の箇所へ波及しないか(推奨技法: regression-selection, checklist-based)

## 7. ガイドワード法による未記載リスクの洗い出し指示(意味的層)

### 7.1 運用手順

1. 先に人間がテストベースを読み、思いつくテスト条件を洗い出して固定する。
2. 着目点1 × 着目点2 × ガイドワードの組を機械的に生成する。
3. 各組の質問テンプレートに沿って、AIに条件候補を出させる。
4. 既出条件と重複する候補は捨て、まだ無い視点だけをマージする。
5. マージした条件には source: "guideword" と、着想元の要件ID/リスクID等を derivedFrom に必ず付ける。

## 8. リスク分析フレームの適用指示(意味的層)

- すべてのテスト条件でリスクスコアが算出済み。

ステークホルダー別影響枠の問い:

- RSF-01 エンドユーザー: この不具合が出たとき、利用者は自力で回避できるか / 気付かずに誤った結果を信じてしまう恐れがあるか
- RSF-02 運用・保守担当: 発生時に原因を特定できる情報（ログ・通知）が残るか / 復旧のための手作業がどれだけ発生するか
- RSF-03 事業責任者: 売上・請求・契約に直接影響する誤りが生じるか / 対外的な説明や謝罪が必要になる規模か
- RSF-04 開発者: 修正時の影響範囲が広く、二次不具合を招きやすい箇所か / 再現条件が特殊で、調査に時間がかかる箇所か
- RSF-05 外部連携先: 連携先へ誤ったデータを送ってしまう可能性があるか / 連携先の処理を止めたり、再送を強いることになるか

制御不全の観点(制御不全パターン枠（自作整理）):

制御ループの捉え方とパターン分類は自作の整理であり、外部の分析手法・規格の逐語転載やそれらへの適合を主張するものではない。

- RCL-01 制御する側: 判断して指示を出す側（利用者・上位機能・バッチ制御など）。
- RCL-02 制御される対象: 指示を受けて状態が変わる側（データ・機器・外部システムなど）。
- RCL-03 指示: 制御する側から対象へ渡る操作・命令・設定値。
- RCL-04 フィードバック: 対象の状態が制御する側へ戻る通知・応答・画面表示・ログ。
