# 2024年テストベース（V02構成）成果物生成手順 — V02汎化検証

本書は `sample/contest_testbase/2024/` 配下の成果物を **誰でも同じ入力から同じ出力に再生成できる** ようにするための手順書である。
対象は ASTER テスト設計コンテスト 2024年版テストベース（`sample/contest_testbase/2024/2024_tdc_open_testbase/2024_tdc_open_testbase/` の PDF 9文書）。

目的は2025年版（V03構成：入場ゲートハブあり）と同一のツール群・同一の投入方法で成果物を生成し、決定的検査の指標を並べて
**V03固有の前提に依存した検査がないかを確かめる回帰ベースラインを作ること**である。指標の対比表は
`docs/ai/regression-baseline.md` に置く。

追跡: GitHub Issue #98（親 #69） / Jira HSKZ-142。

---

## 1. 工程の全体像

| 工程 | 内容 | 使用ツール | 成果物 |
| --- | --- | --- | --- |
| **V-0** | テキスト抽出と抽出品質の記録 | `scripts/extract-testbase-text.sh` | `.work/testbase/2024/*.txt`（コミットしない） |
| **V-1** | ID母集団監査 | `audit_id_population` | `sample/contest_testbase/2024/01_ID母集団監査_2024テストベース.md` |
| **V-2** | 要件分析とテストベースレビュー | `analyze_requirements` / `review_test_basis` | `sample/contest_testbase/2024/07_要件分析結果_2024テストベース.md` / `sample/contest_testbase/2024/08_テストベースレビュー結果_2024テストベース.md` |
| **V-3** | テストケース生成と仕様書レビューの縮小プローブ | `generate_test_cases` / `review_test_specification` | `sample/contest_testbase/2024/14_テストケース生成結果_V02縮小プローブ.md` / `sample/contest_testbase/2024/16_テスト仕様書レビュー結果_V02縮小プローブ.md` |
| **V-4** | データフロー・タイミング分析 | `analyze_data_flow_timing` | `sample/contest_testbase/2024/19_データフロー・タイミング分析結果_V02.md` |
| **V-5** | 回帰ベースラインの作成 | （文書作成） | `docs/ai/regression-baseline.md` |

2025年版に存在する工程B（テスト計画書）・工程C-2（利用状況モデリング・テスト条件抽出）・工程D-1（境界値分析・同値分割）・
工程D-3の探索的チャーター・工程E（差分再展開）は本タスクでは実施しない。V02汎化検証の目的は
**別構成での決定的検査の挙動を観測すること**であり、成果物の網羅ではないためである。
成果物番号は2025年版と対応が取れるよう `01_` `07_` `08_` `14_` `16_` `19_` を踏襲し、実施しない工程の番号は欠番のままにする。

## 2. 前提の導入

### 2.1 poppler-utils（`pdftotext`）

```
# Debian / Ubuntu
apt-get update && apt-get install -y poppler-utils
# macOS
brew install poppler
# Windows
winget install --id oschwartz10612.Poppler
```

`apt-get update` を先に実行しないとパッケージ取得が404になる。未導入のまま `scripts/extract-testbase-text.sh` を
実行すると、導入コマンドを表示して非0終了する。

**本調査で使用した `pdftotext` は poppler 24.02.0 である**（2025年版 `sample/contest_testbase/2025/00_成果物生成手順.md` 2.1 と同一基準）。
本書および payload に記載した `文書名:行番号` はすべて `.work/testbase/2024/*.txt`（この版で抽出したテキスト）の行番号である。
poppler のバージョンが変わると改行位置が変化し**行番号がずれる可能性がある**。行番号が合わない場合は、まず `pdftotext -v` で版を確認すること。

### 2.2 MCPサーバのビルド

```
npm install
npm run build
```

### 2.3 `scripts/extract-testbase-text.sh` の探索先

本タスクで `SRC_ROOT` の解決を修正した。`sample/contest_testbase/<year>/` を優先して探し、無ければ従来の `sample/<year>/` に
フォールバックする。テストベースを `sample/contest_testbase/<year>/` へ再編（コミット `ccff599`）した後は
修正前のスクリプトでは2025年版でも `sample/2025 が存在しません` で失敗していた。抽出オプション（`-layout -enc UTF-8`）・
対象ディレクトリ（`*_tdc_open_testbase`）・ファイル名昇順・出力先（`.work/testbase/<year>/`）は変更していない。

## 3. 実行コマンド

### 3.1 工程V-0: テキスト抽出

```
bash scripts/extract-testbase-text.sh 2024
```

`.work/testbase/2024/*.txt` が9件生成される。抽出物は ASTER 提供資料の逐語テキストになるため `.work/` 配下に置き、
リポジトリにはコミットしない（`.gitignore` で除外済み）。

**2024年 11号のみ双方向制御文字（U+202A〜U+202E, U+200E, U+200F）を 3,858 文字含む。** 2025年版9文書には0件である。
この差の影響を切り分けるため、制御文字を除去した補助版でも工程V-1・V-2の3ツールを実行する（補助版の出力はコミットしない）。

```
mkdir -p .work/testbase/2024-stripped
python3 -c "
import re,os,glob
for f in sorted(glob.glob('.work/testbase/2024/*.txt')):
    t=open(f,encoding='utf-8').read()
    open('.work/testbase/2024-stripped/'+os.path.basename(f),'w',encoding='utf-8').write(re.sub(r'[‪-‮‎‏]','',t))
"
mkdir -p .work/aux-2024-stripped
node scripts/call-mcp-tool.mjs --tool audit_id_population \
  --payload sample/contest_testbase/2024/payloads/audit-id-population.json \
  --documents-dir .work/testbase/2024-stripped --documents-key documents \
  --out .work/aux-2024-stripped/01.md
node scripts/call-mcp-tool.mjs --tool analyze_requirements \
  --payload sample/contest_testbase/2024/payloads/analyze-requirements.json \
  --documents-dir .work/testbase/2024-stripped --documents-key documents \
  --out .work/aux-2024-stripped/07.md
node scripts/call-mcp-tool.mjs --tool review_test_basis \
  --payload sample/contest_testbase/2024/payloads/review-test-basis.json \
  --documents-dir .work/testbase/2024-stripped --documents-key documents \
  --out .work/aux-2024-stripped/08.md
```

制御文字の混入数は次のコマンドで数える。

```
for f in .work/testbase/2024/*.txt; do
  python3 -c "
import sys,re
print(sys.argv[1], len(re.findall(r'[‪-‮‎‏]', open(sys.argv[1],encoding='utf-8').read())))
" "$f"
done
```

```
node scripts/call-mcp-tool.mjs --tool generate_test_cases \

  --out "sample/contest_testbase/2024/16_テスト仕様書レビュー結果_V02縮小プローブ.md"
```

**規模は意図的に絞っている**（テスト条件14件・テストケース21件）。目的は件数の年度比較ではなく、
別構成での**検査の誤検出の有無**の確認である。テスト条件は次のV02固有領域を狙って選んだ。

| テスト条件 | 狙い |
| --- | --- |
| TC-V01 | `EH-100` が V02 では発券機起動のみを指すこと（V03では入場ゲートハブ起動と同一IDで重複する） |
| TC-V02 | `EH-210` が V02 では発券機の会員ログインのみを指すこと（V03ではハブ側のQRコード有効/無効判定と重複する） |
| TC-V03 / TC-V04 / TC-V05 | `EG-210` / `EG-220` の判定が入場ゲート単独で完結すること（V03ではハブへ移管された箇所） |
| TC-V06 / TC-V07 | 入場券情報一覧の上書きタイミングと未使用入場券の無効化 |
| TC-V08 | `EG-310` のゲート開閉制御 |
| TC-V09 / TC-V10 / TC-V11 / TC-V12 | 72号のデータ連携（V02の連携経路。「入場ゲート」「入場ゲートハブ」間データが存在しない） |
| TC-V13 / TC-V14 | 21号 Web予約購入と残数（2025年版と本文が完全一致する文書。差が出ないことが期待値） |

`additionalCoverageTargets` と `coverageCriteriaDeclaration` を宣言し、**網羅対象は必ずケース本文に値・クラス名・状態名を書いている**
（2025年版 3.20 の方針を踏襲）。裏付けなし網羅対象を意図的に作ってはならない。
期待結果の引用文言は2024年テストベースの実在表現のみを使う（#71 の事実照合が通ること自体が観測対象）。

`idPrefix` は `TCS-V` である。`TCS-` にすると `TCS-V01` の番号部が数字のみでないため 4.5 でプレフィックス不一致21件が出る。

## 5. 工程V-1で確定した母集団

**件数は必ず `sample/contest_testbase/2024/01_ID母集団監査_2024テストベース.md` の 2.8 サマリを正とする。**

`.work/testbase/2024`（生の抽出）での実行結果:

- 定義ID総数 113 / 宣言済み 64 / 除外宣言 49 / 未宣言 0 / 母集団反映率 56.6% / テストベース未定義ID数 40 / 未投入文書数 0 / ダイジェスト指摘数 4

`.work/testbase/2024-stripped`（双方向制御文字を除去した補助版）での実行結果:

- 定義ID総数 162 / 宣言済み 104 / 除外宣言 58 / 未宣言 0 / 母集団反映率 64.2% / テストベース未定義ID数 0 / 未投入文書数 0 / ダイジェスト指摘数 4

**宣言母集団（104件）と除外（58件）は補助版の162件を実在母集団として作っている。** 生の抽出では 11号 のID定義行が
1行の先頭に U+202D が入るため定義として認識されず（`extractIdOccurrences` は行頭マーカー直後のIDだけを定義と判定する）、
11号の49件が定義0件になる。生の抽出で報告される「テストベース未定義ID 40件」は、この抽出品質の欠落を数値化したものであり、
母集団宣言の誤りではない。詳細は `docs/ai/regression-baseline.md` 第5章・第6章に記録する。

### 5.1 除外（対象外）の切り分け方針

除外は58件。切り分けの判断基準は2025年版 `sample/contest_testbase/2025/00_成果物生成手順.md` 6.1 と同一であり、
根拠はすべて2024年 01号 の前提・スコープ記述に置いている。「スコープ外」だけの理由は1件もない。

| 除外グループ | 件数 | 根拠 | 対象に残したもの |
| --- | --- | --- | --- |
| 発券機の個別支払い手段処理（`EN-241`〜`EN-243`, `EH-244`, `S-005-02`〜`S-005-16`） | 19 | 01号:198-199「変更していない箇所：発券機での決済処理」／01号:296-299 スコープ外：決済システム（すでにテストエビデンスがあるため）／01号:121-122 差分のない箇所は運用実績で信頼性確保 | 支払い方法の選択分岐 `EH-240` / `S-005-01`、決済成否を契機とする残数の確保・開放 `EK-311` / `EK-321` / `EK-322` |
| 入場ゲートのハードウェア起動・LED制御・ブザー制御・入場管理連携・停止（`EG-100`, `EG-320`, `EG-330`, `EG-400`, `EG-900`） | 5 | 01号:296-301「テスト設計スコープ／スコープ外：入場ゲート（既存と変更点がないため）」／01号:198-200「変更していない箇所：入場ゲートのハード＆ソフト」／01号:152 入場可/不可の伝達方式は既存のまま | QRコード読み取り `EG-210`、QRコード有効/無効判定 `EG-220`、判定結果に基づく開閉制御 `EG-310` |
| 会員登録（`W-001` 系, `W-Mail-001-*`） | 7 | 01号:119-120「会員登録・変更・退会…は保証済み」 | 登録済み会員でのログイン `W-003-01` 以降の予約購入・発券・入場 |
| 退会（`W-002` 系, `E-012`） | 4 | 同上（退会） | 利用可能入場券の有無は予約購入側 `W-008`〜`W-010` |
| パスワード再設定（`W-005` 系, `W-Mail-005-*`） | 8 | 同上（会員情報変更） | 再設定後の認証情報によるログイン `W-003-01` |
| 会員情報編集（`W-007`, `W-007-01`） | 2 | 同上（会員情報変更） | 会員情報紐づけ結果を使う発券 `EH-104` / `EH-312` / `W-014-01` |
| お問い合わせ（`W-012` 系, `W-Mail-012-01`） | 4 | 01号:120「お問い合わせ…は保証済み」 | エラー画面からお問い合わせへの遷移 `W-900-01`〜`W-900-03` |
| 会員登録・会員情報編集・パスワード再設定からのみ参照されるエラー文言（`E-001`〜`E-003`, `E-006`〜`E-011`） | 9 | 参照元画面をすべて除外したため | 予約購入・ログインから参照される `E-004` / `E-005` / `E-013`〜`E-020` |

**2025年版との除外判断の唯一の実質差は入場ゲートである。** 2025年 01号 は「入場ゲートは既存と変更点がないためスコープ外 →
2025年変更点ありとなりスコープ内となる」と自らの記述を上書きしているため2025年版では `EG-*` を全件対象にしている。
2024年 01号 にはこの上書きが無く、01号:296-301 のスコープ外記述がそのまま生きている。そこで同一の判断基準
（「変更点があるか」を根拠に判断する）を適用した結果として、入場ゲートのうち
**時間枠付き入場用QRコードを新たに扱うことになった `EG-210` / `EG-220` / `EG-310` だけを対象に残し**（01号:123 が
入場の流れの確認を依頼し、01号:184-185 が入場可能時間を日から時間枠へ変更している）、
ハードウェア起動・LED/ブザー・入場管理連携・停止の5件を除外した。

### 5.2 2024年版と2025年版のID母集団の差

実在母集団はどちらも162件で、差は1IDだけである。

- 2024年版にのみ存在: `EG-400`（入場ゲートの入場管理システム連携。11号:1175-1176）
- 2025年版にのみ存在: `EH-300`（入場ゲートハブ側の機能。V03構成で追加）

**ID件数がほぼ同じであっても機能の意味は変わっている。** `EG-220` の QRコード有効/無効判定は2024年版では入場ゲート内で
完結し（11号:1110-1113「読み取ったQRコード情報および入場ゲート内で保持している『入場券情報一覧』を基にQRコードの有効/無効を判定する」）、
2025年版では入場ゲートハブへ移管されている。`EH-100` / `EH-210` / `EH-900` は2025年版では発券機側とゲートハブ側の
別機能に同一IDで重複するが（2025年版 6.2）、2024年版では発券機側の意味だけを持つ。

### 5.3 `[medium]`（検出IDが0件）の4件について

`01_` 1.1 のダイジェストで「検出IDが0件」の `[medium]` が4件出る（01号・02号・12号・72号）。
これは9文書すべての全文を投入していること（2.6 が「なし」）で裏付けられる、**文書の性格による正常な結果**である。
0件にするために抜粋を投入したり `idPatterns` を調整したりしてはならない。

なお生の抽出では 11号 も定義0件になるが、これは上記の抽出品質の欠落によるものであり文書の性格ではない。
`08_` 1.1 のダイジェストが 11号 を `[medium]` として挙げないのは、参照IDが208件検出されているためである。

## 6. テストベース全文テキストをコミットしない方針

`.work/` 配下（`testbase/2024/`、`testbase/2024-stripped/`、`rerun-2024/`、`aux-2024-stripped/`）はいずれもコミットしない。
payload・成果物・回帰ベースラインではID・機能名・画面名・章節見出しと短い語句にとどめ、根拠は `文書名:行番号` で示す。
`grep -c 'ゲートハブ' sample/contest_testbase/2024/payloads/*.json` が0であることは、V03固有の記述を持ち込んでいないことの機械的な確認になる。
