# テストベース投入の形式別変換規約

追跡: GitHub Issue #166 / Jira `HSKZ-190`。

## 1. 目的と適用範囲

`docs/roadmap.md` は「テストベースのフォーマットは任意」「バイナリ形式は呼び出し側（MCPクライアント / LLM）が
テキスト化して渡す責務とし、tool 側は『フォーマット不問の自由テキスト』として受け取る」と定めている。
本書はこの**呼び出し側の責務**を具体化する文書であり、「MCPツールへ投入する自由テキストを、
バイナリ原本（Word / Excel / PDF）からどう作るか」だけを扱う。ツール側の入力仕様（フォーマット不問の
自由テキストを受け取る）は変えない。

適用範囲外:

- MCPツールの入力スキーマ・決定的検査ロジック（変更しない）。
- Word の目次ノイズの本文への混入対策そのものの実装（GitHub Issue #168 の担当。本書では規約の言及にとどめる）。
- 新しい入力品質判定区分（IQC-nn）の追加（本書は既存 IQC-01〜IQC-05 を参照するのみで、新規区分は追加しない）。

## 2. 共通原則

- 原本（Word/Excel/PDF）はリポジトリに**原本のまま**保存し、Markdownへ書き起こさない
  （`sample/non_contest_testbase/README.md` の方針）。変換物は `.work/` 配下にのみ出し、コミットしない
  （`.gitignore` で除外済み）。
- 変換は「何を保ち、何を落とすか」を形式ごとに固定し、**同一原本から同一テキストが再現される（決定的）**
  ことを要件とする。変換ツールの版・オプションが変わると決定的検査の結果も変わりうるため、
  版・オプションを固定して記録する（PDF は `pdftotext` の版、Excel/Word は本書の変換規約そのもの）。
- 出力は UTF-8 / LF。表はパイプ表（`| a | b |`）、見出しは Markdown の `#`。これは `src/documentDigest.ts` の
  `extractTableCells` / `parseHeadings` が拾える形であるため、この形式に合わせることで
  `audit_id_population` 等の入力ダイジェスト・表検査（IQC-01/IQC-04）・見出し検査（IQC-03）が機能する。

## 3. Excel（.xlsx）

Excel は OOXML（ZIP + XML）形式であり、素朴な文字列抽出では最低でも次の4点を誤る。

### 3.1 共有文字列の解決

- **保つ**: `<c t="s"><v>3</v></c>` のようなセルは、値 `3` が `xl/sharedStrings.xml` の `<si>` 配列の
  インデックスであり、実際の文字列ではない。インデックスを `xl/sharedStrings.xml` の該当 `<si>` から
  解決したうえで本文へ出す。
- **誤処理したときに何が起きるか**: 未解決のまま数値インデックスを本文へ出すと、表のセルが数値のみになる。
- **対応する IQC**: IQC-01（孤立数値セル）。

### 3.2 自己閉じセル

- **保つ／落とす**: `<c r="B3" s="5"/>` のような自己閉じセルは「値の無いセル」であり、列参照 `r` 属性
  （例 `B3` の列部分 `B`）から列位置を復元したうえで、**値としては何も出さない**（空文字として位置だけ保持する）。
- **誤処理したときに何が起きるか**: 自己閉じセルを読み飛ばして詰めると、以降の列の共有文字列参照が
  ずれ、無関係な文字列や数値が化けて出現する（#163 で対処済みの破損パターンと同種）。
- **対応する IQC**: IQC-01（孤立数値セル）。

### 3.3 ふりがな

- **落とす**: `<si>` 配下の `<rPh>...</rPh>`（読み仮名要素）は**本文へ連結しない**。`<rPh>` の中にも
  `<t>` があるため、`<rPh>` ブロックごと先に除去してから `<t>` を連結する必要がある。
- **誤処理したときに何が起きるか**: `<rPh>` 内の `<t>` まで連結すると、漢字の直後にふりがなの
  カタカナ表記が混入する（実測: ある変換で全体の10%相当の1,568字がふりがな混入）。
- **対応する IQC**: IQC-02（ふりがな混入）。

### 3.4 図形／テキストボックス内テキスト

- **独立セクションとして必ず出力する（本Issue完了条件の必須項目）**: `xl/drawings/drawing<N>.xml` の
  `<xdr:sp>`（図形／テキストボックス）配下の `<a:t>` は、セル抽出だけでは一切出力されない。
  シート単位でセルのパイプ表を出したうえで、そのシートに紐づく drawing がある場合だけ
  `## 図形内テキスト（<シート名>）` という独立セクションを追加で出す。
- **誤処理したときに何が起きるか（＝セクションを省略したときに何が起きるか）**: セル抽出のみだと
  図形内に書かれた説明（例: APIシーケンス図の吹き出しテキスト）が丸ごと消える。この情報は
  `analyze_execution_order` / `analyze_data_flow_timing` に渡す元データとして使われることがあり、
  欠落すると検査対象が縮退する（実測: 付番API仕様書のAPIシーケンスシートで図形14件・図形内テキスト
  （`<a:t>`）53件のうち、セル抽出だけでは0件しか投入されない）。
- **対応する IQC**: **無い**。図形内テキストの欠落は「本文に何も無いこと」であり、投入テキスト単体からは
  宣言（「ここに図形内テキストがあるはずだ」という主張）そのものが存在しないため、宣言と実体の照合を
  構成できない。したがって本規約と参照実装（セクションを必ず出力する）でのみ担保する。将来のIQC候補
  としては記録するが、本Issueでは新規IQC番号を追加しない。

シート単位で `## <シート名>` 見出しを出し、シート順は `xl/workbook.xml` の `<sheet>` 宣言順
（＝ワークブックのシートタブ表示順）で固定する。`sheetN.xml` のファイル番号はシート表示順と一致しない
原本があるため、ファイル番号順に決め打ちしない。

## 4. Word（.docx）

- **見出し**: `w:pStyle` の `w:val` が `Heading<n>` / `heading <n>` / `見出し<n>` のとき、レベル `n` の
  Markdown 見出し（`#`×n）へ対応づける。見出しスタイルが1件も使われていない文書は Markdown 見出しが
  0件になり IQC-03（見出し0件）を招くため、Word文書側で見出しスタイルを使っていることが前提になる。
- **目次**: フィールド（`w:fldSimple` の `w:instr` に `TOC` を含むもの、および `w:fldChar` の
  begin/separate/end 複合フィールドで `w:instrText` に `TOC` を含むもの）の**結果テキストは落とす**。
  目次を本文として投入すると、ページ番号付きの見出し断片が実際の見出し・本文IDと重複してしまう
  （詳細な対策は GitHub Issue #168 の担当。本書では規約として「落とす」ことのみを定める）。
- **変更履歴**: `w:ins`（挿入）は**採用**（中身を残す）、`w:del` と `w:delText`（削除）は**落とす**。
  つまり「すべての変更を反映した最終版」を投入する。コメント（`word/comments.xml`）は投入しない。
- **表**: `w:tbl` を `w:tr`→1行、`w:tc`→1セルとしてパイプ表へ変換する。セル内改行・タブは半角空白へ
  畳む（畳まないと `src/documentDigest.ts` のパイプ表解析が崩れ IQC-04 の表崩れを招く）。セル内の
  `|` は `\|` にエスケープする。

## 5. PDF

- `pdftotext -layout -enc UTF-8` に固定する。既存の `scripts/extract-testbase-text.sh` を、この規約の
  参照実装として位置づける。
- `-layout` を外すと表の列構造が失われ、決定的検査の結果が変わる（実測: `audit_basis_contradictions` の
  総候補数が 218 件／176 件、`analyze_requirements` の出力文字数が 190,899字／128,010字と、
  `-layout` の有無だけで変動する）。この差は IQC-01（孤立数値セル・表破損由来）/ IQC-04（表崩れ）の
  指標へ間接的に反映され、単独の新規判定区分にはしない。
- PDF は見出し構造（アウトライン）を持たないため、IQC-03（見出し0件）が常に出る。これは既知の限界として
  受け入れる。
- `pdftotext` の版は抽出結果の再現性に影響する（版が変わると根拠位置がずれることがある）ため、
  回帰測定時は版を記録する。回帰ベースラインは poppler 24.02.0 で測定している
  （`docs/ai/regression-baseline.md` 2章）。

## 6. Markdown / プレーンテキスト

変換不要。原文をそのまま投入する。

## 7. JSON

- 変換不要。JSON テキストをそのまま投入してよい。
- ID の見なし方: 値として現れる `"id"` / `"requirementId"` 等のフィールド値を ID とみなす。JSON は
  Markdown 見出しを持たないため IQC-03 が出る。ID 抽出はパターンマッチベース（`testbasis://id-patterns`）
  であり、既定パターンで拾えない ID 体系はツール側の任意入力（`idPatterns`）でパターンを指定する。
- 整形（pretty-print）した JSON の方が、キーと値が行分割されるため行頭マーカー判定
  （`src/documentDigest.ts` の行頭処理）が安定する。1行に詰め込んだ（minify した）JSON は避けることを
  推奨する。

## 8. 規約項目と判定区分（IQC-nn）の対応表

既存 IQC の判定内容・閾値の詳細な説明は `src/resources/inputQualityCriteria.ts` を正とし、本書では
逐語コピーせず参照にとどめる。

| 規約項目 | 形式 | 対応IQC | 検出層 |
| --- | --- | --- | --- |
| 共有文字列の解決 | Excel | IQC-01 | あり |
| 自己閉じセルの位置復元 | Excel | IQC-01 | あり |
| ふりがな（`<rPh>`）の除去 | Excel | IQC-02 | あり |
| 図形内テキストの独立出力 | Excel | — | **なし（将来のIQC候補）** |
| 見出しの `#` 対応 | Word / PDF | IQC-03 | あり |
| 目次の除去 | Word | — | なし（#168 で扱う） |
| 変更履歴の反映 | Word | — | なし（将来のIQC候補） |
| 表構造の保持（`-layout` 固定・セル結合） | PDF / Excel / Word | IQC-04 | あり |
| 双方向制御文字 | PDF / Word | IQC-05 | あり（ツール側が除去） |

「検出層なし」の項目について、なぜ決定的検査にできないかを補足する。

- **図形内テキストの独立出力（Excel）**: 図形内テキストが欠落しているかどうかは、投入されたテキスト
  そのものを読んでも分からない。「本来ここに図形内テキストがあったはずだ」という宣言（例: 「シートXに
  図形が3件ある」という母集団宣言）が入力側に存在しないため、宣言と実体を突き合わせる決定的検査を
  構成できない。この欠落は規約と参照実装（セクションを必ず出力する）でのみ担保する。
- **目次の除去（Word）**: 目次を落とし忘れたかどうかは、目次と本文の区別が投入テキスト側の宣言として
  残らない限り機械的に判定できない。GitHub Issue #168 で目次由来のノイズ対策を扱う想定であり、
  本書では規約（結果テキストを落とす）の言及にとどめる。
- **変更履歴の反映（Word）**: `w:del`/`w:ins` を正しく処理したかどうかは、投入後のプレーンテキストからは
  判別できない（削除文言を採用しても、挿入文言を採用し忘れても、見た目は「普通の文章」になる）。
  本書の規約（削除は落とす・挿入は採用する）で運用を固定する。

## 9. 参照実装

| 形式 | 参照実装 | 出力先 |
| --- | --- | --- |
| PDF | `scripts/extract-testbase-text.sh <year>` | `.work/testbase/<year>/*.txt` |
| Excel | `node scripts/extract-testbase-xlsx.mjs <in.xlsx> [--out <path>]` | `--out` 省略時は標準出力 |
| Word | `node scripts/extract-testbase-docx.mjs <in.docx> [--out <path>]` | `--out` 省略時は標準出力 |

Excel / Word の参照実装は `scripts/lib/ooxml.mjs`（OOXML共通のZIP読み出し・純関数群、外部依存ゼロ）を
土台にした Node.js（ESM `.mjs`）の小さなCLIである。ZIP展開は `node:zlib` の `inflateRawSync` のみで行い、
`xlsx` / `mammoth` のような npm パッケージは追加していない。

例:

```bash
bash scripts/extract-testbase-text.sh 2025
node scripts/extract-testbase-xlsx.mjs sample/non_contest_testbase/2026-08_digital-agency_atenabango-fuban-api_spec.xlsx \
  --out .work/ingestion/fuban-api.txt
node scripts/extract-testbase-docx.mjs path/to/spec.docx --out .work/ingestion/spec.txt
```

**参照実装は「規約を満たす最小の一実装」であり、呼び出し側が別手段（別ツール・別スクリプト・手動変換）で
変換してもよい。規約（2章〜7章の「保つ／落とす」）を満たすことが要件であり、実装手段そのものを
強制するものではない。**
