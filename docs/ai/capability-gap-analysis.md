# ケイパビリティギャップ分析: 過去コンテスト成果物と同等以上を目指すために

*過去10チーム（2023〜2025年 決勝進出）の発表資料全文から「そのチームの思考を成立させている道具」を35項目として抽出し、本MCP v0.12.0 の resource / tool / 純関数の実装と1件ずつ突き合わせた。あわせて、`sample/2026/品質比較レポート_再レビュー.md` で提案した Tier 1〜3 改修を適用したと仮定したシミュレーションを行い、なお埋まらない不足を洗い出す。*

---

## 0 結論

| 段階 | 35項目中の充足 | 到達水準 |
| --- | --- | --- |
| 現状 v0.12.0 | **11項目 (31%)** ＋部分6項目 | 下位2チーム（Teamやま・不撓不屈）と拮抗 |
| Tier 1〜3 適用後 | **14項目 (40%)** ＋部分6項目 | 中位まで。11ヒポポタマス・考えるアシカbeta・ミックスベジタブルには届かない |
| 同等ライン | **26項目程度** | Phase C（テストアーキテクチャ層）を越えた先 |

不足は散らばっておらず、**3つの層に集中している**。

1. **テストアーキテクチャ層が存在しない** — 過去4チームが独立工程として出している。条件→ケースの2段しかなく、「テストをどう束ね、どの順で、どの環境で回すか」の層が丸ごと無い。
2. **17技法中13技法にエンジンがない** — とくに use-case-based / scenario-based / decision-table / config-matrix。本課題の本丸である「購入→発券→入場のE2E」が手動宣言に落ちる。
3. **多軸マトリクスの相互補完がない** — 双方向カバレッジは隣接2者（要件↔条件、条件↔ケース）のみ。離れた軸どうしの直積を取って「片側にしかないもの」を検出する構造がない。

逆に、**リスク分析・ガイドワード・ペルソナの知識リソースは既に過去チーム相当かそれ以上**である。ここは作り直す必要がない。

## 2 シミュレーション: Tier 1〜3 適用後に何が出て、何が出ないか

同じ 2026 年テストベース（V03）を、改修後のパイプラインで通した場合を工程順に追う。

### 工程1: テスト計画

**出る** — `create_test_plan` の15章。Tier1③で文書ダイジェスト表（「11号要求仕様書 35,525字/検出ID 47件」）が付き、抜粋投入が見える化される。

**出ない**
- **テスト目的の導出チェーン**（爆裂たまご）。同チームは「依頼書から依頼者の期待を掴む → 期待に対するテスト要求 → 自社テスト戦略 → **テスト目的4つ**」を立て、以降の観点抽出・品質特性割当・テストタイプ決定・優先度をすべてこの4目的で束ねている。本MCPのテンプレートには「目的」の記入欄はあるが、**目的を導出する型がなく、目的が下流工程を束ねる構造もない**。結果、テストタイプ選定（5.2節の○×表）の根拠が「なんとなく該当する」に留まる。
- **ステークホルダーマップ（影響力×関心度の得点化）**（爆裂たまご・AVATES）。AVATES は STEP1特定→STEP2ニーズ抽出→STEP3影響力×関心度のマッピングと**得点化**→STEP4 重視対象に絞って要求導出、という4段を踏む。本MCPは persona frame にペルソナはあるが**2軸評価と絞り込みの型がない**。計画書11.2は「名前・役割・連絡先」の表止まり。

### 工程2: テストベースレビュー／要件分析

**出る** — ID体系・重複・未解決参照・曖昧語・数量表現の横断集約（Tier1③で30秒/60秒の取りこぼしが減る）・境界値候補。`audit_id_population` で母集団監査（41件→実在約135件ベース）。

**出ない**
- **文書間の仕様矛盾**（ミックスベジタブル）。同チームは 13号4P/21P の戻るボタン挙動相違、21号 W-008-04 と 22号 画面遷移図の相違、分け与えメール本文の誤りなど**8件**を指摘した。現状の決定的検査は `findDuplicateIds`（同一IDの重複定義）／`findUnresolvedReferences`（未解決参照）／`analyzeTermUsage`（用語ゆれ）までで、**「同一対象について複数文書が異なることを言っている」を検出する検査が存在しない**。
- **原因結果グラフ（CEG）**（考えるアシカbeta）。仕様の論理関係をモデル化して、文章では読み取りづらい曖昧さ・抜けを検知する手段。本MCPに該当なし。

### 工程3: テスト分析（テスト要求・観点・リスク）

**ここは既に強い。** 18観点カタログ／ガイドワード15×16／リスクフレーム3軸＋5区分＋制御不全パターン枠／ペルソナ4象限／ユーザーストーリーマップ／ドメイン分析7観点。爆裂たまご・ねこにサウナ・考えるアシカのリスク＆ペルソナ面は、リソースとしては揃っている。

**出ない**
- **ラルフチャート（信号因子／誤差因子／状態因子／制御因子への分解）**（考えるアシカbeta）。ガイドワードは「どう揺さぶるか」の辞書であって、**対象を因子に分解して水準を割り当てるモデルではない**。同チームはラルフチャートで因子・水準を洗い出してから技法を適用しており、ペアワイズ／デシジョンテーブルの入力を体系的に得る仕組みになっている。本MCPは因子の洗い出しが完全に呼び出し側任せ。
- **利用時品質モデル**（ねこにサウナ）。`quality://characteristics/product` は**製品品質8特性のみ**で、利用時品質（有効性／効率性／満足性／リスク回避性／利用状況網羅性）がない。TC-050〜054 のようなステークホルダー由来条件を品質特性に接続できず、宙に浮く。
- **リスクの多軸スコア＋ステークホルダ別影響の構造化**（考えるアシカbeta）。同チームは重篤度を**4軸**（直接影響／波及影響／短期的金銭影響／長期的金銭影響）×5段階、発生頻度を**2軸**（利用頻度／故障しやすさ）×5段階で持ち、さらに**ステークホルダ（入場者／係員／経営者／だんだん市補助金担当）ごとの影響**を1リスクにぶら下げている。本MCPは影響度1軸×発生可能性1軸×変更差分の3軸。frame にステークホルダー影響の問いはあるが、**リスク×ステークホルダの行列としてスコア化する枠がない**。

### 工程4: テストアーキテクチャ設計 — **層そのものが無い**

過去**4チーム**（appli 2023／AVATES 2024／考えるアシカ 2023／不撓不屈 2025）が独立工程として成果物を出している。内容はテストコンテナへの分割、コンテナの責務定義、コンテナ間の依存関係、実行順序、クリティカルパス、優先度の色分け（最優先／状況に応じて／完成度向上用）。考えるアシカはさらに**コンテナごとに詳細図を作り「テストの意図がテストケースまで途切れない」ことを構造で担保**している。

本MCPは テスト条件 → テストケース の2段で、**間の層がない**。結果、55条件をどう束ね、どの順で、誰が、どの環境で実行するかが成果物に一切出ない。テスト設計コンテストでは独立した評価軸であり、ここが空白である限り構造的に上位に行けない。**同等ラインの分水嶺はここ。**

### 工程5: テスト設計

**出る** — BV／EP／ST ＋ Tier1① の網羅対象裏付け検査（形式的100%が潰れる）＋ Tier2④ の decision-table / pairwise。

**出ない** — 技法カタログは17技法を定義しているが、**エンジンがあるのは4技法だけ**である。

| data-lifecycle-test | ❌ | |

とくに致命的なもの:

- **ユースケース／シナリオ設計**。11ヒポポタマスは 5シナリオ×パターンを抽出し、正常系/準正常系/異常系に分類し、シナリオ一覧を作った。ねこにサウナ・Teamやまもシナリオテスト設計書を独立成果物として出している。**購入→発券→入場のE2Eは本課題の中心**なのに、本MCPはこれを `additionalCoverageTargets` の手動宣言に落とす。サンプルが自ら「シナリオテストの厚みが不足」と書いた原因は、意欲ではなく**エンジンの不在**である。
- **構成・環境マトリクス**。11ヒポポタマスは OS×ブラウザ×解像度×機種を一覧化し、「シングルカバレッジで網羅する」「ただし MacOS は日本の一般家庭での利用が低いため最新と最古の2つに絞る」と**絞り込みの根拠まで明記**した。21号文書には対応ブラウザ・OSが明記されており、本課題で必ず問われる。本MCPは TPC-10（構成・環境）という観点カテゴリを持つだけ。
- **テストデータ設計**。11ヒポポタマスは時間枠残数管理表（休園日設定つき）／アカウント管理表／決済管理表（発券機・Web別）を作った。テスト計画書10.2にデータ要件の表はあるが、**データ設計そのもののツールがない**。

**出ない（最大）— 多軸マトリクスの相互補完**

11ヒポポタマスの思考の核はここにある。同チームは5つの直交マトリクスを作った。

1. プロダクトリスク × テスト方法
2. プロダクトリスク × ユースケース
3. 機能（画面）× シナリオ（通過順序を数値で記入）
4. ユースケース × シナリオ
5. シナリオ × パラメータ

そして各マトリクスに**「片側にあって他方にないものが見つかったらテスト分析をやり直して追加する」**という運用を明文化している。これは単なる可視化ではなく、**軸を変えて何度も網羅性を検算する**手続きである。

本MCPの双方向カバレッジは `buildConditionTraceability` / `findUncoveredConditionIds` などで**隣接2者**（要件ID↔テスト条件、テスト条件↔テストケース）のみを見る。**離れた軸どうし（リスク×観点カテゴリ、ペルソナ×機能、シナリオ×パラメータ）の直積を取って空セルを検出する仕組みがない。** 決定的検査を武器にすると謳いながら、最も決定的に計算しやすいこの検算をやっていない。

### 工程6: テスト実装・実行準備

**出る** — Test size 分類によるテストレベル配分の妥当性チェック（考えるアシカbeta相当）。

**出ない** — コンテナ／テストスイートの依存関係とクリティカルパス（不撓不屈）、モニタリング計画とSLO・合格基準の事前合意（Teamやま）、リグレッションスイートの再利用可能な形での切り出し（Teamやま）。

### 工程7: 保守・変更追従

**出る** — `reexpand_threshold_changes`。**唯一、過去チームを超え得る領域。** ミックスベジタブルの Re:Spec はフェーズ2（反映）のみ実装で、フェーズ1（仕様書からの閾値抽出）は構想止まりと自ら述べている。本MCPは仕様書テキストを入力に取れるため、フェーズ1に踏み込める位置にある。

## 4 改訂ロードマップ

## 5 方針についての注意

**目標を「過去成果物の見た目の再現」に置いてはならない。** 過去チームの強みは人間のモデリングであり、MCPがそれ自体を代替することはできないし、する必要もない。

MCPが提供すべきものは次の2つである。

1. **思考を強制するフレーム** — RDRA・STAMP/STPA・ラルフチャート・テストコンテナといった型を resource として与え、呼び出し側LLMが「その型を埋める」ことでしか出力できないようにする。すでに guideword / risk frame / persona frame がこの形で成功している。
2. **手抜きを検出する決定的検査** — 埋めたつもりで埋まっていないこと（空セル、裏付けのない網羅宣言、実在しない引用、どのコンテナにも属さない条件）を機械的に暴く。ここは人間チームが構造的に苦手な領域であり、**Phase C・D が本MCPの本当の勝ち筋**である。

したがって Phase A（検査）と Phase C・D（構造）を優先し、Phase E の上流モデリングは resource 追加が中心なので後段でよい。Phase B は本課題では B-3（シナリオ設計）だけが突出して重要である。

## 6 最短経路の提案

「同等以上」への最短は次の順である。

```
A-1,A-2,A-3  →  サンプル再生成（既存ツール総動員）
             →  B-3 design_scenario_flows
             →  C-1,C-2 テストアーキテクチャ層
             →  D-1 audit_cross_matrix
             →  再度サンプル再生成 ＝ 同等ライン到達の判定点
             →  B-1,B-4 / E-1,E-2 / F-1,F-2
```

A → B-3 → C → D の4手で ❌18 のうち #17 #19 #20 #21 #22 #34 #35 が埋まり、充足は **21〜22項目（60%超）**に達する。これが「過去のどのチームとも正面から比較できる」最低ラインである。
