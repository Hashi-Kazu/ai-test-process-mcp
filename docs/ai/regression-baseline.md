# 決定的検査の回帰ベースライン（2025年版 V03 × 2024年版 V02）

## 1. 目的と適用範囲

本書は、**決定的検査を持つ全ツール**が**特定のテストベース構成に依存していないかを判定するための基準値**を記録する。
決定的検査を持たないツール、またはテスト計画書系ツール（後述のC群）は対象外とする。

管理対象は次の3群へ分類する。列の意味は次のとおり。「テストベース由来入力」は年度別テストベース文書、または
テストベースから導出された上流成果物のどちらを入力に取るか。「決定的検査の判定区分」はツールが持つ区分ID接頭辞
（`BC-` `CMX-` `TDN-` `PDC-` `TAC-` `DCC-` `CBC-` など）。「本書での指標番号」は第5章の指標番号（未設置のものは
「未着手（別Issueで追加）」）。

C群と区別する基準は「入力が年度別テストベースに由来するか」であって、`documents` 引数の有無ではない。
`analyze_data_flow_timing`（指標10）が既にこの基準で対象化されている先例である。

- **基準とするもの**: 同一のツール群・同一の投入方法で、構成の異なる2つのテストベースへ適用したときの決定的検査の出力件数。
- **比較の軸**: 2025年版テストベース（V03構成：入場ゲートハブあり）と 2024年版テストベース（V02構成：入場ゲートハブなし）。
- **いつ再測定するか**:
  1. `src/` 配下の決定的検査ロジック（`testBasisAnalysis.ts` / `idPopulationAnalysis.ts` / `testCaseAnalysis.ts` /
     `testSpecificationAnalysis.ts` / `dataFlowTimingAnalysis.ts` / `basisContradictionAnalysis.ts` /
     `groundingNormalization.ts` / `requirementsAnalysis.ts` / `documentDigest.ts` / `testPurposeAnalysis.ts` /
     `crossMatrixAnalysis.ts` / `deliverableConsistencyAnalysis.ts` / `coverageBalanceAnalysis.ts` /
     `testDesignNotationAnalysis.ts` など）を変更したとき。決定的検査の本体が `src/tools/<name>.ts` 内の
     レンダリング関数に置かれているツールがある（`design_test_architecture` の `src/tools/designTestArchitecture.ts`
     など）ため、`src/` 直下の解析モジュールだけを見ていると再測定の要否を取りこぼす。
     未着手のB群（指標追加後に再測定対象へ入る）: `testConditionAnalysis.ts` / `causeEffectAnalysis.ts` /
     `thresholdExtraction.ts` / `thresholdChangeAnalysis.ts` / `factorHandoverAnalysis.ts` /
     `stakeholderWeightingAnalysis.ts` / `testSizeAnalysis.ts` / `userStoryMapAnalysis.ts` /
     `exploratoryCharterAnalysis.ts` / `businessRequirementAnalysis.ts` / `nextToolAnalysis.ts` / `derivedFromRefs.ts`。
  2. 新しい決定的検査を追加したとき。
  3. `scripts/extract-testbase-text.sh` の抽出条件、または `pdftotext` の版を変えたとき。
     `scripts/extract-testbase-xlsx.mjs` / `scripts/extract-testbase-docx.mjs`（`docs/ai/testbase-ingestion.md`
     の変換規約の参照実装）の変換条件を変えたときも同様に再測定対象へ含める。
  4. `docs/ai/testbase-ingestion.md` の変換規約を変えたとき。同書2章〜7章の「保つ／落とす」および8章の規約項目とIQCの
     対応が変われば、同一原本から作られる投入テキストそのものが変わるため、指標19（形式間一致度）を含む全指標が
     影響を受ける。項目3が参照実装（スクリプト）の変更を対象とするのに対し、本項目は規約本体の変更を対象とする。
  5. ツールのレンダリング（出力の組み立て・件数上限・`verbose` の扱い）を変えたとき。決定的検査の判定区分・件数が
     変わらなくても出力量は変わりうるため、項目1〜4では拾えない。指標20（ツール別出力文字数）を再測定する。
- **適用範囲外**: テスト計画書系ツール（`create_test_plan` / `review_test_plan` / `revise_test_plan`）はテストベース文書を
  入力に取らないため、構成差の影響を受けない。本書の対比表には含めない。上表のC群がこれに相当する。

**決定的検査の件数をそのまま仕様欠陥の件数として扱わないこと。** 件数は「宣言と実体を機械的に突き合わせた結果の件数」であり、
偽陽性（PDF→テキスト変換に起因するもの、文書の性格による正常な結果）を含む。妥当性の判断は意味的層（呼び出し側）が行う。
2025年版の読み取り注意は `sample/contest_testbase/2025/00_成果物生成手順.md` 3.8 に、2024年版の注意は
`sample/contest_testbase/2024/00_成果物生成手順_V02汎化検証.md` 5章に書いてある。

追跡: GitHub Issue #98（親 #69） / Jira HSKZ-142。GitHub Issue #171 / Jira HSKZ-195（本書の管理対象を全ツールへ拡大）。

## 3. 対象テストベースの選定と2023年版を使わなかった理由

Issue #98 の本文は **2023年版テストベース**を汎化検証の対象とする想定だった。実測の結果これは成立しないため、
汎化検証の対象を **2024年版**へ変更した。

### 3.1 2023年版が使えない実測事実

`sample/contest_testbase/2023/2023_tdc_open_testbase/2023_tdc_open_testbase/` の9文書に対する `pdfinfo` の Producer と、
`pdftotext -layout -enc UTF-8`（poppler 24.02.0）の抽出文字数:

| 文書 | Producer | ページ数 | 抽出文字数 |
| --- | --- | --- | --- |
| 01号 テスト依頼書 | Microsoft® PowerPoint® for Microsoft 365 | 26 | 17,884 |
| 02号 概要書 | Skia/PDF m115 Google Docs Renderer | 11 | 16,142 |
| **11号 園内チケットシステム要求仕様書** | **Microsoft: Print To PDF** | **32** | **32** |
| 12号 ハードウェア仕様書 | Skia/PDF m115 Google Docs Renderer | 6 | 6,102 |
| 13号 発券機画面仕様書 | Skia/PDF m115 Google Docs Renderer | 36 | 31,292 |
| 21号 Webチケットシステム要求仕様書 | Skia/PDF m115 Google Docs Renderer | 37 | 68,270 |
| 22号 Webチケットシステム画面仕様書 | Skia/PDF m115 Google Docs Renderer | 41 | 41,616 |
| 71号 入場券仕様書 | Skia/PDF m115 Google Docs Renderer | 6 | 10,867 |
| 72号 データ連携仕様書 | Skia/PDF m115 Google Docs Renderer | 10 | 23,428 |

2023年 11号 は `Microsoft: Print To PDF` で出力されており **テキスト層を持たない**。32ページに対して抽出結果は32文字である。
`EH-` / `EG-` / `EK-` / `EN-` / `Z1-` / `Z2-` のID母集団はこの文書だけで定義されるため、2023年版では
`audit_id_population` の実在ID母集団が構築できず、決定的検査へ投入できない。

### 3.2 2023年版を使うために必要なこと（本タスクのスコープ外）

2023年版を回帰ベースラインへ加えるには 11号 のOCRが必要である。**OCRは本タスクのスコープ外とし、実施していない。**
OCRを導入する場合は、抽出テキストの精度（IDの誤認識率・行番号の安定性）自体が指標へ影響するため、
**別Issueとして起票する必要がある**。本書ではその必要性の記録にとどめ、Issue の作成は行っていない。

### 3.3 2024年版を選んだ理由

- 9文書すべてが `pdftotext` でテキスト抽出できる。
- `ゲートハブ` の出現が9文書すべてで0件であり、`EG-220 QRコード有効/無効判定` が入場ゲート内で完結する
  **V02構成**（11号:1110-1113）である。したがって「入場ゲートハブありという前提に依存した検査」を検出できる。
- 5文書（12号・13号・21号・22号・71号）が2025年版と**完全一致**するため、差が出た指標について
  「構成差に起因するのか、検査の汎化不良に起因するのか」を切り分けられる。

### 指標19: 同一内容を複数形式で投入したときの決定的検査の一致度

指標1〜18は「同一形式（PDF）× 構成の異なる2つのテストベース」の対比だった。指標19は軸を変え、
「同一内容 × 異なる形式」で決定的検査の出力がどこまで一致するかを扱う。追跡: GitHub Issue #174 / Jira HSKZ-198。

#### 19.1 一致度の定義

- 指摘キー＝「判定区分（または出力の節見出し）」＋「対象キー（ID／ラベル）」。根拠位置（`文書名:行番号`）は必ずキーから外す。
  根拠位置は形式が変わればほぼ確実にずれるため、キーに含めると一致度が意味を持たなくなる。
- 一致度＝`|A∩B| / |A∪B|`（Jaccard、%）。あわせてA側のみ/B側のみの件数を必ず併記する。B側のみが0であれば「差は
  取りこぼし方向のみ」を意味する。
- サマリ行の各集計値（総候補数・severity内訳など）は補助指標として併記する。件数一致は指摘の同一性を保証しない
  （同数でも中身が入れ替わっているケースを検出できない）ため、主指標はキー集合の一致とする。
- 一致度の計算は使い捨てスクリプトで行い `.work/` に置く。`scripts/` へコミットしない（本Issueの計測手法であり、
  ツールの参照実装ではないため）。

#### 19.2 形式カバレッジ

| 形式 | 原本 | 変換規約 | 現時点の測定 |
| --- | --- | --- | --- |
| PDF | `sample/contest_testbase/2025/**/*.pdf` | 同書5章 | 測定済（19.4） |
| Excel | `sample/non_contest_testbase/*.xlsx` | 同書3章 | 測定済（19.3） |
| Markdown | Excel規約変換の出力そのもの | 同書6章 | 規約上Excelと同一表現へ収束するため一致度100%（構成上自明、測定不要） |
| JSON | Excelと同一内容を再直列化した測定用データ | 同書7章 | 測定済（19.3、暫定） |
| Word | `sample/non_contest_testbase/format_reference/word/2026-08_digital-agency_common-feature-spec_v2.1.docx`（および新旧対照表docx） | 同書4章 | 測定済（19.6）。19.3のようなID内容一致度比較は原本の内容がExcel（宛名番号）と異なるため不成立。表現形式（`#`見出し・パイプ表・目次除去）の収束を確認 |

`docs/ai/testbase-ingestion.md` の変換規約（3章・4章・6章）により、Word / Excel / Markdown は変換後に同一表現
（UTF-8/LF・パイプ表・`#`見出し）へ収束する設計である。したがって Markdown は Excel 規約変換の出力を投入すれば
必然的に一致度100%になり、独立した測定を要しない。Word のリファレンス原本は#173で追加済み（`format_reference/`
配下）であり、Word 行も実測済みとなった（19.6）。ただし、Word原本（共通機能標準仕様書）と宛名番号Excel原本は
別ソース（前者は共通機能標準仕様書、後者は宛名番号管理）のため、19.3のようなID集合の内容一致（Jaccard）比較は
そもそも成立しない。Word行の実測は19.6で「表現形式への収束」（構造レベル）として行う。実測が意味を持つ軸は

Excel/Markdown収束系と同じ表現に収束しているか」（19.6）の2軸である。

`audit_id_population`、payload = `sample/non_contest_testbase/payloads/audit-id-population.json`。

| 項目 | Excel（＝Markdown、規約準拠変換） | JSON（同一内容を再直列化） |

解釈: **形式差（説明可能）であり、汎化不良ではない。** `idPatterns`（`testbasis://id-patterns` の既定値）が

> （前後の`|`を除去し`|`で分割して各セルをtrim）、それ以外の非空行→`text[]`、最後に`JSON.stringify(doc, null, 2)`。
